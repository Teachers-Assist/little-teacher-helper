## 判準：三類訊息

系統要告訴人的事分成三類，**任何新規則都必須先歸類，再套用該類的檢驗標準**。完整說明見 `specs/004-alerts-and-feedback/spec.md`。

| 類型     | 受眾 | 主動性           | 檢驗標準                                       |
| -------- | ---- | ---------------- | ---------------------------------------------- |
| **警示** | 老師 | 主動打擾         | 有明確可採取的行動？會不會天天觸發？           |
| **證據** | 老師 | 完全被動，待查   | 查得到？看得懂？老師知道它存在？               |
| **提示** | 學生 | 操作當下即時回饋 | 指向概念而非只指向行動？學生處理得了嗎？       |

**本文件收錄「警示」類（主動打擾老師）與「監視器（證據）」類（被動留痕、待查）。** 前者見「現行規則」，後者見「監視器（證據級）機制」。學生端的「提示」類不在本文件範圍。

若一條訊息的「為什麼」答案是「因為程式沒寫好」，它不屬於三類中的任何一類 —— 那是 bug 或技術債。

## 現行規則

實作於 `src/lib/anomalyDetection.ts`（純函式、無 I/O），由 US4 monitoring endpoint 與 US8 dashboard endpoint 共用，確保兩處判斷一致。

### 共同前提

所有規則都只在以下條件成立時才判定：

- 任務 `status === 'ACTIVE'`（已結案 CLOSED、小老師已標記完成 HELPER_COMPLETED 皆不判）
- 任務未封存（`isArchived === false`）

### 規則一：任務停擺

| 項目         | 內容                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------- |
| **狀態**     | 🟡 004 定案，待實作（現行實作為舊版，見下方「沿革」）                                     |
| **觸發條件** | 距離**最後一次登記活動**已超過閾值；任務從未有登記時，起算點退回任務建立時間（滑動視窗） |
| **閾值**     | **24 小時**                                                                              |
| **排除**     | 登記筆數已達班級學生總數（全班登滿）時不判，即使小老師未按「我登記完了」                  |
| **不要求**   | 不要求任務有指定小老師；不要求任務有設截止時間                                            |
| **來源**     | 002 FR-035 建立；004 US6 / FR-102 ~ FR-105 重整                                           |

**這條規則同時是「裝置長時間未同步」的實作方式。** 伺服器無法即時觀測「某台裝置正離線中」—— 離線裝置不產生任何資料，缺席無法被歸因。但裝置離線導致資料傳不上來，會表現為「這個任務長時間沒有新資料進來」，與「學生忘記登記」共用同一個訊號，而**兩者對老師的行動相同**（去看一下卡在哪裡）。因此本規則以**任務層級的活動時間**作為裝置心跳的代理指標，不需要 Device entity。代價是無法指出「是哪一台裝置」—— 在班級尺度下，老師問一聲就知道。

### 規則二：截止日零登記

| 項目         | 內容                                                                              |
| ------------ | --------------------------------------------------------------------------------- |
| **狀態**     | 🟡 004 定案，待實作（現行實作為舊版，見下方「沿革」）                              |
| **觸發條件** | 任務有設截止日；已過**截止日當天 08:00**（`Asia/Taipei`）；全班零登記              |
| **閾值**     | **08:00 絕對時鐘**（非相對時距）                                                  |
| **排除**     | 任務於截止日當天 08:00 **之後**才建立者不判（避免剛建立就被喬），仍受規則一保護    |
| **來源**     | 002 FR-035 建立；004 US6 / FR-106 ~ FR-107 重整                                    |

**為什麼用絕對時鐘**：老師早自習就會知道，還有一整天可以補救。原本的「距截止 6 小時」搭配當時硬編的 23:59:59 截止，實際上要到晚上 18:00 之後才提醒，老師已經下班。

**依賴**：004 FR-108 將新建任務的截止時間預設由 `23:59:59` 改為 **17:00**。時間標準化之後，08:00 必然早於截止，原本的邊界問題（截止早於 08:00、提前量太短）自然消失。

## 涵蓋矩陣

004 重整的核心目的，是消除下表右下角原本存在的空格。

| | 有設截止日 | 沒設截止日 |
| --- | --- | --- |
| **有指定小老師** | 規則一 + 規則二 | 規則一 |
| **沒指定小老師** | 規則一 + 規則二 | **規則一** ← 重整前此格為空 |

重整前規則一要求 `assignedSeatNumber != null`、規則二要求 `dueDate != null`，兩者交集導致「沒指定又沒截止」的任務異常涵蓋率為零 —— 而這正是 `vision.md` 第 5 節理想場景所描述的建立方式（「誰負責收可以之後再指定，截止時間也可以彈性設」）。**偵測空窗落在產品最推薦的使用方式上。**

**維護要求**：新增任務欄位或改動規則前置條件時，MUST 重新檢查此矩陣不得出現空格（對應 004 SC-025）。

## 已知限制

### 繳交類任務的停擺假陽性（已知並接受）

`src/lib/task.ts` 的設計是「未繳交」不存 `NOT_SUBMITTED`，而由「查無記錄」推導。因此系統**無法區分「小老師還沒動」與「小老師跑完一輪、答案是沒人交」** —— 兩者在資料上都是零筆 Record。

後果：

- 規則二會對「全班確實都沒交」的任務誤報
- 規則一因無活動時間戳而退回 `createdAt` 起算，24 小時後誤判停擺
- 規則一「登滿全班就不判」的排除條件，在繳交類任務上只要有人沒交就達不到

**2026-07-20 決議：接受此假陽性**，不改資料模型、不新增活動訊號。理由是「全班都沒交」實務上罕見，老師點進任務即可辨識。若日後誤報頻繁，優先解法是讓「已確認未繳交」也存一筆記錄（根治），而非在規則上加特例。

### 無法指出是哪一台裝置

見規則一說明。屬設計取捨，非缺陷。

## 監視器（證據級）機制

**監視器 = 記錄但不主動通知、也不呈現為異常。** 平常安靜、不做判斷、不消耗老師注意力，只在老師起疑、主動查案時產生價值（監視器比喻，004 討論確立）。這些機制**不需通過警示的檢驗標準**（值不值得打擾、會不會太吵），因為它本來就不打擾；它要通過的是另一組標準：**查得到、看得懂、老師知道它存在**。

列於此處，以利判斷「某件事該做成監視器（被動留痕）還是警示（主動打擾）」——兩者常被混為一談。

| 監視器機制 | 記錄什麼 | 不做什麼 | 位置 | 狀態 |
| --- | --- | --- | --- | --- |
| **紀錄順序處理者名單** | 每筆 Record 被哪些座號、依什麼順序、在什麼時間處理過（座號 + 時間，不留前值） | 不比對、不判定「誰冒用 / 誰搗亂」，判斷留給老師 | 任務細節頁（`RecordHandler` 子表） | 🟡 004 US4 定案，待實作 |
| **非指定者代登記可見性** | 每筆的登記者座號 + 是否為指定小老師（`recorderSeatNumber` / `isAssignedRecorder`） | **不升級為警示**——「不擋、但可見」（vision 承諾裝置）；代登記可能是同學補位的健康行為 | 任務細節頁 | ✅ 已實作（004 US4 提升視覺重量） |
| **封存後才進來的登記標示** | 任務封存後才同步進來的登記（沿用 002 L232「照常寫入」） | 不阻擋寫入、不主動通知 | 任務細節頁 | 🟡 004 FR-097a 定案，待實作 |

**與「警示」的分界**：同一件事若做成警示，就必須通過「有明確可採取行動嗎？會不會天天觸發？」；做成監視器則不必。例如「非指定者代登記」曾被評估升級為警示，最終決定維持監視器級——因為成因（老師交代的修正 / 誤操作 / 蓄意）系統無從判斷，主動喊等於替老師預判。

## 待盤點候選

尚未評估或尚無資料可判斷的候選規則。每加一條都必須定義：觸發條件、閾值、嚴重度、是否會大量觸發（警示疲勞）、以及對應的老師可採取行動。

- 截止前 X 小時登記率仍偏低（非 0）—— 規則二只判零登記，「開了頭但進度落後」目前無人管
- 任務建立後長時間零進度 —— **已由 004 重整後的規則一涵蓋**，保留條目以免重複提案
- 指定小老師以外的人代登記比例過高
