## 2026-05-29 · Vision 初稿完成，Spec 調整前的前置問題

完成 `vision.md` 初稿後，由 AI agent 檢視文件所識別的 5 個缺口。在調整現有 spec 或新增 spec 前需要先解決。

---

### ✅ 1. QRCode 機制：房間 vs. 任務（優先級：最高）

**問題**：現有 spec 的架構是「掃碼加入房間，房間內有多個登記項目」。vision.md 的成功場景描述的是「每個任務有自己的 QRCode，小老師掃碼直接進入被指派的任務」。這兩個架構的資料模型、權限設計、離線行為都不同。

**這個問題卡住**：幾乎所有 spec 的細節——進入流程、任務指派、離線同步、身份識別。

**決定結果**：

保留房間架構，一個班級一張 QRCode。小老師掃碼進入房間後，自己從任務清單中選擇要負責的任務（一個小老師可負責多個任務）。**不做任務專屬 QRCode**——讓老師為每個小老師合成對應的任務碼，會增加操作步驟，複雜度不值得。

讓小老師自行選擇任務而非系統或老師代為指定，符合「學生對自己的行為負責」的設計理念。

**資料模型影響**：任務（Task）需新增「指定的小老師」欄位（nullable）。非指定者仍可登記，但系統標記實際登記者的座號。相關 spec 見 spec.md User Story 2 與 Key Entities 更新。

取捨說明：小老師可能選錯任務（責任在學生）；所有小老師都能看見所有任務（班級事務本就公開，可接受）。

---

### 🔲 2. MVP 功能邊界

**問題**：目前哪些功能確定在 MVP、哪些不在，沒有明確的清單。

**這個問題卡住**：無法判斷一個 user story 是否在範圍內，也無法估計開發量。

**需要逐一確認的功能**：

| 功能                                | 在 MVP？ | 備註                |
| ----------------------------------- | -------- | ------------------- |
| 繳交狀況登記                        | ✅ 是    | 現有 spec 核心      |
| 成績登記                            | ✅ 是    | 新增 User Story 6   |
| 小老師身份識別（選座號 + 承諾裝置） | ✅ 是    | 已納入 User Story 2 |
| 小老師自行標記任務完成              | ✅ 是    | 新增 User Story 7   |
| 班級公開看板（學生可見）            | ❌ 否    | 移至下一階段        |
| 老師例外通知機制                    | ❌ 否    | 移至下一階段        |
| 家長端                              | ❌ 否    | 明確為後續版本      |

**決定結果**：MVP 包含繳交登記、成績登記、小老師身份識別、小老師標記任務完成。班級公開看板、老師通知機制、家長端均不在 MVP 範圍。

---

### ✅ 3. 「一般學生」角色定義

**問題**：系統目前定義了老師、小老師、家長三種角色，但非小老師的一般學生從未被說明。

**決定結果**：MVP 中一般學生不是系統使用者，不需進入系統。班級公開看板（一般學生唯讀介面）列為下一階段開發，屆時再定義此角色的進入方式與權限。

---

### ✅ 4. 老師通知的觸發條件

**問題**：vision.md 的設計目標是「老師是被通知後的決策者，不是主動監控者」，但觸發條件完全未定義。

**決定結果**：老師例外通知機制不在 MVP 範圍內。MVP 中老師仍需主動開啟系統查看狀況。通知機制的觸發條件設計移至下一階段，屆時再完整規劃。

---

### ✅ 5. 「任務」物件的欄位定義

**問題**：vision.md 多次提到「任務」，但它的欄位只能從敘述中零散拼湊。現有 data-model.md 是以「房間」為核心設計的，與 vision 的方向可能有出入。

**這個問題卡住**：資料模型更新、API 設計、離線同步邏輯。

**目前已知的任務欄位**：

- 登記項目類型（繳交 / 成績 / 其他）
- 截止時間（可彈性設定）
- 指派的小老師（可後來再改）
- 是否開放修改
- 任務狀態（進行中 / 小老師已標記完成 / 老師已結案）

**待確認的欄位**：

- 任務可以指派給多個小老師嗎？
- 任務的有效期間是一天還是可跨多天？
- 任務可以複製到下一天嗎（例如每日作業登記）？

**決定結果**：核心欄位已確立（見 spec.md Key Entities）。以下子問題不影響 MVP 開發，移至下一階段：任務是否可跨多天有效、任務是否可複製到下一天。

### 下一階段 spec 規劃

> 此區塊記錄本階段決定不在 MVP 內、但需要在下一次 spec 規劃時處理的項目。

- **老師例外通知機制**：系統在特定情況下主動通知老師（長時間未同步、任務截止前提醒、異常登記等），觸發條件待設計。目標是讓老師成為「被通知後的決策者」而非「主動監控者」。

- **家長端功能**：家長接收通知、查看班級資訊的完整設計（參見 vision.md 第 6、7 節）。

### 🔲 全站網路 / 同步狀態 policy

**問題**：網路連線狀態、同步狀態、警告觸發（裝置太久沒同步）等行為散落實作於：

- `src/components/NetworkStatus`、`src/components/SyncIndicator`（小老師端登記頁、任務清單頁底部）
- `src/hooks/useNetworkStatus`（小老師端散落使用）
- `src/lib/offline/syncController`（同步控制核心）

但沒有統一的 spec 描述以下事項：

1. **各畫面該顯示什麼狀態**：哪些 banner、何時顯示、何時消失、文案
2. **警告升級規則**：離線多久顯示「換個地方試試」、未同步多久通知老師（具體閾值）
3. **失敗 retry 策略**：指數退避？重試上限？放棄條件？
4. **老師端「裝置同步狀況」視圖**：002 班級狀況 tab（US4）的警告區會用到「裝置太久沒同步」訊號，但目前老師端完全沒有對應的視覺呈現與資料源
5. **/join 離線時的處理**：003 換座號流程把人推回 /join，必須統一處理「使用者在沒網路時抵達 /join」的情境

**為什麼卡住**：影響 002 US4（班級狀況 tab 的警告區資料源）、003（小老師端入口 / 換座號 / 登記過程的網路提示），但本身不屬於任一 feature 範圍。

**處理方向**：開新 feature folder（例如 `specs/004-network-and-sync-policy/`）作為下一階段獨立議題。需先盤點現有元件實際行為，再對照 vision 第 6 節「老師是被通知後的決策者」決定警告升級規則。

**前置盤點**：需要做的事 ——

<a name="延伸議題異常條件完整清單2026-06-26-新增"></a>

#### 延伸議題：異常條件完整清單（2026-06-26 新增，owner：老師 / 使用者）

併入原因：這份清單的核心候選項目（裝置長時間未同步的閾值、通知時機）跟上面「警告升級規則」（第 2 點）、「老師端裝置同步狀況視圖」（第 4 點）本質是同一個決策——都需要先有裝置層級的同步資料才能設計閾值，因此排進 004 feature 一併規劃，不單獨開項目。

目前 MVP 只實作兩條任務層級異常（指定座號 24h 無登記、所有人未登記且距截止 < 6h）。下一階段需要由使用者把「哪些情況該算異常 / 該提醒老師」完整盤點並排優先序，候選包含但不限於：

- **已截止但登記率 < 100%**：本次評估後**先不加**，理由是幾乎每個已截止任務都會觸發 → 警示變吵；且已截止後學生已鎖定，性質偏「結果」而非「可補救的異常」。若要加，需設計收斂條件（例：僅在剛截止 N 小時內、或登記率低於某門檻才提醒）。
- 裝置長時間未同步（見下方「裝置長時間未同步」異常偵測段落，需資料模型支援）。
- 其他待盤點：指定小老師以外的人代登記比例過高？任務建立後長時間零進度？截止前 X 小時登記率仍偏低（非 0）？

每加一條都要定義：觸發條件、閾值、嚴重度、是否會大量觸發（避免警示疲勞）、以及對應的老師可採取行動。確定後寫入對應 feature 的 spec（FR-035 的「至少包含」可擴充）與 plan.md 閾值表。

<a name="導師-vs-科任"></a>

### 🔲 導師 vs 科任老師的資料模型與流程支援

**問題**：台灣老師有兩種類型，目前 spec 與 data model 都隱含假設「一個老師管多個獨立班級」，但兩種類型實際需求很不同。

**導師（一個班級、所有科目）**：

- 主要動作：建立任務、管理學生、看異常
- Dashboard 只看一個班級
- 「我的班級」清單只有一筆
- **現有架構足以支援**，UIUX 上無需特殊調整

**科任（多班級、同一科目）**：

- 主要動作：**同一份任務通常要同時建立在多個班級**（例：五年甲乙丙的數學作業繳交）
- 跨班級報表最有價值（多班加總後問題才會集中浮現）
- Dashboard 看到的「班級」多個
- **現有架構運作但有顯著痛點**：必須一班一班手動建任務，重複勞動；無法跨班看「同一份任務」的總覽

**對 data model 的潛在影響**：

- 目前 `Task` 直接綁 `Room`（1:N）
- 科任老師「同一份任務套用到多個班級」→ 每班各生成一個 `Task` 物件 → 報表分散
- 可能解法：
  - **TaskTemplate** 抽象：老師建立範本 → 套用到多個班級 → 每班自動生成 Task，但記得 `templateId`
  - 跨班級報表以 `templateId` 聚合（例「五年甲乙丙的數學作業」總覽）
  - 報表 / 異常清單需要支援「按 templateId 分組」與「按 roomId 分組」兩種視角

**對任務 / 班級建立流程的影響**：

- 建立任務時可以多選班級（一次套用至多班）
- 指定座號可能要每班分別指定（座號 24 在不同班是不同人）
- 「快速建立多個班級」（例「我教五甲乙丙丁戊」一次建五個）值得考慮

**MVP 階段的處置**：

002 US8 已透過 UIUX 處理兩種老師：

- Dashboard 異常清單以「[班級名] · [任務名]」格式顯示，多班級老師可清楚識別歸屬
- 統計按跨班級加總呈現
- 側欄「我的班級」可展開清單作為多班級導航中樞

不在 MVP 範圍內：

- TaskTemplate 抽象 / 一次套用多班的任務建立流程
- 跨班級報表聚合（按 templateId）
- 一次建立多個班級

**處理方向**：開新 feature folder（例 `specs/005-teacher-types-and-templates/`）作為下一階段獨立議題，啟動前需先觀察 MVP 上線後科任老師實際的痛感程度。

### ✅ 「裝置長時間未同步」異常偵測（002 FR-035）—— 已由 004 US6 解決

> **2026-07-26 結案**：004 US6 推翻「需裝置心跳資料模型」的前提。改用**任務層級活動時間**（滑動視窗）作為代理指標——「裝置離線導致資料傳不上來」表現為「任務長時間沒有新登記」，與「學生忘記登記」共用同一訊號，且對老師的行動相同（去看卡在哪）。已實作於 `detectAnomalies` 規則一（`TASK_STALLED`），用既有資料即可運作，不需 Device entity。代價：無法指認「是哪一台裝置」（原理限制、可接受）。詳見 `specs/anomaly-rules.md` 規則一與 `specs/004-alerts-and-feedback/spec.md` US6。下方原始討論保留為歷史。

**問題（原始）**：002 FR-035 / T128 將「裝置長時間未同步」列為班級狀況 tab 與 dashboard 的異常判斷條件之一，但目前資料模型沒有任何「裝置心跳 / 最後上線時間」可供判斷 —— `Record.syncedAt` 只記錄單筆記錄的同步時間，無法推導某台裝置整體是否長時間離線。

**MVP 階段的處置（2026-06-26 實作 002 時決定，owner：老師 / 使用者）**：

- 先**略過**此條異常。002 US4 / US8 的異常偵測（`src/lib/anomalyDetection.ts`）只實作可用現有資料判斷的兩條規則：
  1. 指定座號 24h 無登記
  2. 所有人未登記且距截止時間 < 6h（具體閾值由 002 plan.md 記錄）
- 「裝置長時間未同步」需要新增裝置層級的追蹤（例如 Device entity 或 lastSeenAt 心跳 + client 端定期上報），屬資料模型擴充，延後處理。

**待決**：是否值得為此異常新增裝置追蹤？需觀察 MVP 上線後老師是否真的需要「裝置離線」這類提醒（vs. 既有的兩條任務層級異常已足夠）。

> 「異常條件」完整清單的盤點待辦，已併入上方[「全站網路 / 同步狀態 policy」](#-全站網路--同步狀態-policy)段落的[「延伸議題：異常條件完整清單」](#延伸議題異常條件完整清單2026-06-26-新增)，一併排進 004 feature 規劃。

## 2026-07-20 · 004 spec（警示、證據與回饋）撰寫期間新增的待解問題

<a name="門禁紀錄深度"></a>

### 🔲 紀錄留痕的深度：是否升級到保留「前值」

**背景**：004 US4 為紀錄覆蓋建立留痕機制，讓老師起疑時有證據可查（監視器比喻）。留痕深度經兩次收斂：

- 初步（2026-07-20 上午）採「門禁等級」：只留最初建立者 + 最後修改者。
- **修正定案（2026-07-20）**：升級為**順序處理者名單** —— 每次處理都追加（座號, 時間）依序保留。**因此「同一筆被多人覆蓋、中間修改者遺失」的問題已解決**，老師看得到完整經手鏈。詳見 004 US4 / FR-092。

**仍未解的一件事**：名單保留「誰、何時、第幾手」，但**不保留「每一手把它改成什麼值」（前值）**。老師查得到經手人與順序，查不到內容的變化。

**待決**：是否值得再升級為完整 audit log（每次變更額外保留前值）？這是留痕的最後一層深度。小學班級情境下此需求可能不高，MVP 先不做。需觀察上線後老師是否真的遇到「知道誰動過、也知道順序，但因為不知道改成什麼而無法判斷」的情況。

**追記（2026-08-11）：留痕深度變成不對稱的了。** 為了修「刪除會抹掉經手鏈」（測試回饋問題四），`RecordHandler` 新增了 `action` 欄位（`RECORD` / `DELETE`），老師端展開名單時會看到「12 號**刪除**・時間」。於是現在的狀態是：

- **刪除**這個動作，老師看得到「發生了什麼」——12 號把這一格清空了
- **覆蓋**這個動作，老師只看得到「12 號經手過」，看不到「把 80 改成 90」

同樣是「別人動了我登的東西」，一個說得出內容、一個說不出。這不是刻意設計，是修 bug 的副產品——`action` 只是為了讓刪除不被誤讀成「改了值」而加的最小資訊，不是往 audit log 邁進的第一步。

**這使原本的待決更值得問，但也給了折衷選項**：完整 audit log（保留每一手的前值 / 新值）之外，還有一個中間檔——只在**覆蓋他人**時記錄值的變化，同座號連續修正仍不記。成本遠低於完整 audit log，也剛好對準老師真正會起疑的情境。

**另一個必須一起想清楚的張力**：FR-093 的相鄰去重（同座號同動作不追加）是為了避免正常修正灌爆名單。一旦要保留值，`8 號登 80 → 90 → 100` 就會變成「只留一筆、且不知道是哪個值」或「留三筆、名單膨脹」二選一——**保留前值與相鄰去重在設計上互斥**，不能只加欄位而不重新決定去重規則。

## 2026-08-05 · 離線換座號與 syncQueue 去重鍵的張力

<a name="離線換座號去重鍵"></a>

### 🔲 離線換座號是否安全：syncQueue 去重鍵不含座號

**背景**：規劃「讓學生離線時幾乎所有操作皆可」時，檢視是否連「換座號」也開放離線就地進行（不必回線上限定的 `/join` 重新入場）。

**前因後果**：`addToSyncQueue` 的去重鍵是 `type + taskId + studentId`（**不含座號**，`src/lib/offline/queue.ts:39-44`），命中既有 op 時 `nextSyncOp` 直接**整包覆寫 payload**（含 `recorderSeatNumber`，`queue.ts:26-27`），佇列裡仍只剩一個 op。老師端看到的「多人經手」順序處理者名單，是 server 端 `/api/sync` 對**每一個實際收到的 op** 依 `shouldAppendHandler` 追加建成的（`src/app/api/sync/route.ts:102-112`）。

因此在**共用裝置**情境——「座號 A 離線登記某 (task, student) 但尚未同步 → 座號 B 經換座號後對同一 (task, student) 再登記」——A 那筆 pending op 會被 B 的 op **原地吃掉**：server 從頭到尾只收到一個 `recorderSeatNumber=B` 的 op，**A 這一手永不進資料庫、也不進經手鏈**。老師看不出中間 A 經手過，直接違反「離線期間的（座號, 時間）MUST NOT 因離線遺失或錯置經手鏈」（004 US4 / FR-092 / FR-097、SC-023）——而多人經手正是本專案「班級自治仍留痕可查」的招牌信任機制。

現況之所以**沒有**這個 bug：換座號被 003 US4 逼上線（`clearRoom` + 導回線上限定 `/join`），連線會先把 syncQueue **排空**，A 的 op 先同步進經手鏈，B 才換座號重登 → 兩手各自成 op → 鏈 = [A, B]，完整。也就是說「換座號必須線上」這條約束，實際上承載了離線經手鏈的正確性。

**決策（2026-08-05）**：本次「學生端離線操作修復」採**選項一**——換座號**維持線上限定**，離線時於「登記者：」badge 直接擋下（不 `clearRoom`、不導 `/join`，僅顯示兒童語氣提示），**不改動去重鍵**。同步以 Service Worker 讓離線主流程（選任務 / 回列表 / 硬重整 / 登記）可用。已將此調整回寫 `003 spec US4 / AS4 / FR-075` 與 `data-model.md` 換座號段。

**離線偵測的可靠度（2026-08-05 補充）**：實測 `navigator.onLine` 在 DevTools Network Offline 與「連了 WiFi 但無網（lie-fi）」都仍回報 `true`、`offline` 事件也不觸發，故**不足以** gate 破壞性動作。因此換座號改用實際探測伺服器的 `isServerReachable()`（`src/lib/offline/connectivity.ts`，打一個 `/api` 路徑，SW 不介入 `/api` → 離線必失敗）。**刻意只有換座號這個「不可逆且無法復原」的動作用探測**；其餘離線判斷（sync gate、join 停用鈕、refresh/load、指示燈、預熱、導覽 SPA/整頁選擇）維持 `navigator.onLine`——這些即使誤判，最壞只是送出一個會被既有重試 / 快取 / 錯誤訊息接住的請求，不造成資料遺失。若日後要讓指示燈 / join 提示在 lie-fi 下也準確，宜建一個「以 fetch 成敗更新的集中連線狀態 store」而非到處打 API（暫緩，無明確需求）。

**待決**：若日後要支援**離線換座號**，最低必須先把去重鍵擴充為 `taskId + studentId + recorderSeatNumber`——同座號重登同一項仍併成一筆（該座號最後一手，符合 FR-093 連續同座號去重），**不同座號**則各自成獨立 op，由 `handledAt` 依序併入經手鏈（FR-097）。此改動牽涉 reconcile / 測試成本較高，且需相應更新 004 FR-097 與 003 US4，暫緩至有明確需求再評估。

## 2026-08-11 · 經手鏈改掛格子後浮現的呈現缺口

<a name="孤兒經手鏈不可見"></a>

### 🔲 已無登記的格子，其經手鏈在老師端看不到

**背景**：2026-08-10 修「刪除會抹掉經手鏈」（測試回饋問題四）時，`RecordHandler` 的 key 由 `Record.id` 改為 `(taskId, studentId)`，並把刪除記成一手。資料層因此**刻意允許**「該格已無 Record、但經手鏈還在」的狀態——那正是要保留的證據。詳見 `data-model.md §6` 與 004 FR-093a。

**缺口**：資料留住了，但**畫面沒有出口**。`/api/records` GET 是以 `Record` 為主體查詢、再把鏈併進每一筆（`src/app/api/records/route.ts`），所以只有「還存在的登記」帶得出鏈。於是：

- **A 登記 → B 刪掉 → A 補回**：老師看得到完整的 `A → B(刪) → A`（已驗證）
- **A 登記 → B 刪掉，沒人補回**：老師看到的是「未登記」，與「從頭到尾沒人登過」**畫面完全相同**。鏈躺在資料庫裡，沒有任何 UI 讀得到它

**為什麼這個缺口比看起來嚴重**：漏掉的正好是最壞的情境。有人補回的版本，資料至少是對的；沒人補回的版本，**資料是錯的（該生其實交了卻顯示未繳），而且線索完全不可見**。老師連「這裡發生過事」都不會知道，也就不會去查。這使 004 US4「班級自治仍留痕可查」在最需要它的那一格失效。

**尚可接受的理由（暫不做的依據）**：004 US8 的「完成但登記太少」與 US6 的異常偵測仍會從**數量**這一側接住——整體登記數偏低會被喊出來。只是老師被引導到的是「有人沒登」，而非「有人登了又被刪」，判斷方向會偏。

**待決**：是否要讓任務細節頁把「無登記但有經手鏈」的格子也標示出來？需一併決定：

1. **資料怎麼拿（2026-08-11 釐清：後端幾乎免費）**——`/api/records` 的 `handlerRows` 查詢**本來就撈出整個任務的鏈**（沒有 join `Record`），孤兒鏈已經在 `chains` 這個 Map 裡，只是 `records.map(...)` 走的是現存登記，沒被認領的就在那一行被丟掉。所以這不是「拿不到資料」，是**回應沒有位置裝它**：這支 API 的單位是「一筆登記」，而鏈的單位是「一個格子」，登記被刪掉後那個格子在陣列裡沒有身分（實測：回應直接從 4 筆變 3 筆，該生連空殼都沒有，因此 `rec.handlers` 無從寫起）。

   最省的做法是把回應改成 `{ records, orphanHandlers }`——server 端約 5 行，學生端 `cacheSyncedRecords` 的呼叫點改成 `.records` 一行。**先前傾向的「另開唯讀端點」已否決**：當初顧慮動到離線快取路徑，但實際改動只是一個屬性存取，為此多養一支端點不划算。
2. **成績類的版面要重整（2026-08-11 補：這才是主要成本）**——兩種任務類型的落地難度差很多：
   - **繳交類**（`TaskResultView` 的 `rosterRows`）全班每人本來就有一整列 `<li>`，且該列已在容納 `HandlerTrail`（`w-full` 自動換行），未登記者只是 `rec` 為 null → **接上資料即可，接近零成本**
   - **成績類**把未登記者放在 `grid-cols-2 sm:grid-cols-3 md:grid-cols-4` 的 **chip 網格**，一格只有座號 + 姓名、約 1/4 寬，**塞不下可展開的順序名單**
   
   因此成績類必須先決定「被清空過」的學生該待在哪裡。傾向把他們**從 chip 網格移進「登記明細」列表**、值顯示為已清空——語意上他們本來就不屬於「從沒被碰過」那一群。代價是「登記明細」的定義從「有值的人」變成「這一格有歷史的人」，屬於既有區塊的語意變更，需確認老師讀得順。
3. **怎麼呈現**——這一格「不是未登記，是被清空過」。用什麼語氣？是否比照 FR-097a 走**證據級**（被動可見、不主動喊、不用警告色）？若做成主動警示，等於新增一條異常規則，要回頭對齊 `anomaly-rules.md`
4. **要不要進報表**——匯出的「未登記名單」是否要區分這兩種未登記。`lib/report.ts` 是 `[...students]` 逐人建列、未登記填 `notRecorded`，每人都有一行，加標記不受版面限制（與成績類網格的困難相反）

**整體評估（2026-08-11）**：後端 ~5 行、繳交類 ~10 行、報表 ~20 行；成本集中在成績類 UI（~60–80 行）與上述第 2、3 點的語意決定。工程量不大，卡點在決定。
