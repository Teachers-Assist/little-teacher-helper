# Feature Specification: 警示、證據與回饋機制 (Alerts & Feedback)

**Feature Branch**: `004-alerts-and-feedback`
**Created**: 2026-07-20
**Status**: Draft
**Input**: 對現有程式碼做「老師端警示 / 學生端錯誤回饋」全面盤點後識別的落差集合 —— 同步失敗的靜默路徑、老師端狀態呈現的誠實性、登記當下的存檔回饋、紀錄覆蓋的留痕、任務生命週期的語意錯置

**前置依賴**: `specs/001-little-teacher-helper/`、`specs/002-class-management/`、`specs/003-helper-onboarding/` 已實作完成。本 feature 在其上做補齊與修正，不取代原 spec。

**編號沿革**: `open-questions.md`（2026-06-25）原預留 `specs/004-network-and-sync-policy/`。經 2026-07-20 討論後**擴大範圍並更名** —— 因為盤點發現落差不只在網路與同步，也包含身份問責的留痕機制與老師端呈現的誠實性，這些與網路同步無關但同屬「系統要讓人知道發生了什麼」這一主題。原預留條目的內容全部併入本 feature。

**明確排除（out of scope）**:

- **老師端主動通知管道**（PWA 推播 / email）—— vision 第 6 節「老師是被通知後的決策者」的完整實現，牽涉技術選型與家長端規劃，保留為後續 feature。本 feature 只確保「老師主動來看時，看到的是完整且誠實的資訊」。
- **「指出是哪一台裝置沒同步」** —— 伺服器無法即時觀測「某台裝置正離線中」，因為離線裝置**不產生任何資料**，而缺席無法被歸因。這是原理限制，不是實作取捨。

  但需要特別記錄：`open-questions.md` 原先「此異常需裝置心跳資料模型，故延後」的結論，**在本 feature 被推翻**。US6 改以**任務層級的活動時間**作為心跳的代理指標，用既有資料即可偵測出「有東西卡住了」，不需要新增 Device entity。真正被排除的只剩「指出是哪一台裝置」這一件事 —— 而老師拿到「這個任務停擺了」這個訊號時，可採取的行動與知道裝置編號時相同。
- **非指定者代登記 / 紀錄被覆蓋，升級為警示** —— 維持證據級，不主動喊。

  2026-07-20 複審時釐清了一個重要區分：US4 的門禁紀錄上線後，原本混為一談的「非指定者代登記」其實是兩件事 —— **甲**：非指定者登了一筆全新的（原本無人登過），這是同學補位、是健康行為；**乙**：非指定者改掉別人已登好的（最初建立者 ≠ 最後修改者），這才是「覆蓋他人紀錄」。原先的否決之所以正確，是因為舊概念太粗，會把甲也染上異常色彩。

  即使拆分後只針對乙，經討論仍決定**維持證據級**：覆蓋的成因（老師交代的修正 / 誤操作 / 蓄意）系統無從判斷，主動喊等於替老師預判。監視器平常不喊，老師起疑再查。

## 對應原則（簡述，完整內容見 `specs/vision.md`）

- **鷹架不是黑盒**（原則三）→ 失敗必須可見，且提示要指向概念而非只指向行動
- **可逆性決定保護強度**（原則一）→ 不可逆的覆蓋行為必須留痕；留痕是「讓學習空間存在」的前提，不是成本問題
- **圍欄 = 越界時讓看守者知道**（原則二）→ 「可見」的定義是「老師來查的時候查得到」，不等於「系統跳出來喊」
- **承諾裝置**（第 7 節）→ 留痕若無人查閱，機制效力大幅下降；學生需知道系統在記錄，但用視覺事實而非道德說教
- **使用者是兒童**（前提）→ 學生只看得到他能處理的事；超出能力的細節給老師，學生端只留「去找老師」

## 三類訊息的判準 _(本 feature 的核心方法論)_

盤點過程中發現，把所有「系統要告訴人的事」混為一談會導致誤判 —— 有些東西該主動打擾，有些東西該安靜待查，有些東西該在操作當下立刻出現。本 feature 建立三分法，**任何新增的訊息都必須先歸類，再套用該類的檢驗標準**：

| 類型     | 受眾 | 主動性             | 檢驗標準                                                     |
| -------- | ---- | ------------------ | ------------------------------------------------------------ |
| **警示** | 老師 | 主動打擾           | 老師有明確可採取的行動嗎？會不會天天觸發（警示疲勞）？       |
| **證據** | 老師 | 完全被動，待查     | 查得到嗎？看得懂嗎？老師知道這個東西存在嗎？                 |
| **提示** | 學生 | 操作當下即時回饋   | 指向概念（為什麼）而非只指向行動（按這裡）？學生處理得了嗎？ |

**「證據」類的特殊性**：它**不需要通過警示的檢驗**（值不值得打擾、會不會太吵），因為它本來就不打擾。這對應 vision 原則二對圍欄的定義 —— 「違規行為要**可見、可補救**」，可見的意思是「你來看的時候看得到」，不是「它會跳出來喊」。

設計比喻（討論時確立，寫入以利後續判斷）：**證據類機制像監視器** —— 平常安靜、不做判斷、不消耗任何人的注意力，只在有人來查案時產生價值。但監視器有兩個前提：**要掛在查得到的地方**（老師知道去哪查），且**要掛在顯眼處**（學生知道它存在，嚇阻力來自被看見而非偷拍）。

**刷除規則**：若一條訊息的「為什麼」答案是「因為程式沒寫好」，它不是三類中的任何一類 —— 它是 bug 或技術債，該修該重構，不該佔用使用者的注意力，也不該進入本 feature 的 User Story。

## User Scenarios & Testing _(mandatory)_

> 優先序依**傷害嚴重度**排定，而非依身分或落差類型。判準：資料會不會遺失 > 信任會不會被破壞 > 體驗好不好。

### User Story 1 - 同步失敗要有出口 (Priority: P1)

小老師的登記在送不出去時，必須被告知，且必須有下一步。目前 `/api/sync` 回傳的 `conflicts` 完全未被解析，重試三次後項目從 pending 濾除、不再嘗試也不標記，資料實質消失而學生毫無所覺。本 US 要求：解析 conflicts、區分「可重試」與「不可重試」、重試耗盡後升級為「去找老師」、`SyncIndicator` 補上失敗態。

**Why this priority**: 這是全系統唯一一條**資料會靜默消失**的路徑，且學生全程以為已儲存。它同時違反 vision 第 2 節表格中「按了送出沒反應 → 系統有外部依賴」與「同步之後同學看得到 → 資料同步就不再只是我的」兩個學習時機 —— 現在學生學到的是錯的：「我按了就會好」。

**Independent Test**: 讓任務進入鎖定狀態（老師結案）→ 學生離線登記數筆 → 恢復連線 → 同步回傳 409 conflicts → `SyncIndicator` 顯示失敗態而非停在「N 筆待上傳」→ 提示指出這幾筆送不出去且應找老師 → 重新整理頁面後失敗態仍在（不因重整而消失）。

**Acceptance Scenarios**:

1. **Given** 佇列中有操作且 `/api/sync` 回傳 207（部分成功）, **When** `processSyncQueue` 處理回應, **Then** MUST 解析 `conflicts` 陣列，成功項目移出佇列、衝突項目標記為衝突態（不得與「尚未嘗試」混為一談）
2. **Given** `/api/sync` 回傳 409（全數衝突）, **When** client 處理, **Then** MUST NOT 將這些操作視為「待重試」持續累加 retryCount
3. **Given** 衝突原因為「任務已鎖定」或「找不到該任務」（不可重試）, **When** client 分類, **Then** MUST 標記為**不可重試**並停止重試，直接進入告知流程
4. **Given** 衝突原因為網路層失敗（可重試）, **When** client 分類, **Then** 依重試策略繼續嘗試【待確認：重試策略見下方 Requirements】
5. **Given** 某操作重試次數達上限, **When** client 判定放棄, **Then** MUST NOT 靜默從佇列濾除；MUST 保留並標記為需人工處理
6. **Given** 佇列中存在不可重試或已放棄的操作, **When** `SyncIndicator` 渲染, **Then** MUST 顯示**失敗態**（與「同步中」「待上傳」視覺可區分），文案指出有幾筆送不出去 + 下一步是找老師【文案待定稿】
7. **Given** 佇列中有未送出的資料且失敗態已出現, **When** 學生重新整理頁面, **Then** 未送出的資料 MUST 保留（不因重整消失）；系統 MUST 重置重試判定並重新嘗試同步一次；若仍無法送出，失敗態 MUST 重新出現（資料任何情況下都不得靜默消失）
8. **Given** 老師已移除該學生 / 已封存或刪除該任務, **When** 學生端持舊快取送出登記, **Then** 系統回傳的衝突 MUST 走上述流程被學生看見，而非靜默丟棄

### User Story 2 - 老師看到的狀態必須誠實 (Priority: P1)

「班級狀況」tab 的 monitoring 資料載入失敗時，目前 `warnings` 停留空陣列，畫面顯示綠色勾勾與「目前沒有需要注意的事」—— 把**載入失敗呈現為一切正常**。本 US 要求區分「確認無異常」與「無法確認」兩種狀態，並補上 002 spec AS3 已要求但未實作的閾值 / 時間資訊。

**Why this priority**: 其他所有落差都是「少給了東西」，只有這一條是「給了錯的東西」。本產品的核心承諾是「老師可以放心把管理責任交出去」（vision 第 3 節），一個會謊報平安的警示系統比沒有警示系統更糟 —— 老師會據此關掉電腦。這破壞的不是體驗，是產品成立的前提。

**Independent Test**: 斷開網路或讓 `/api/rooms/[id]/monitoring` 回 500 → 開啟老師端「班級狀況」tab → 畫面 MUST NOT 顯示「目前沒有需要注意的事」→ MUST 顯示「現在讀不到班級狀況」之類的無法確認狀態 + 重試入口；恢復後重試 → 正常顯示警示卡片，且每張卡片帶有時間 / 閾值資訊。

**Acceptance Scenarios**:

1. **Given** monitoring endpoint 回傳非 2xx 或 fetch 拋錯, **When** 老師檢視班級狀況 tab, **Then** MUST NOT 呈現「目前沒有需要注意的事」空狀態；MUST 呈現**無法確認**狀態並提供重試【文案待定稿】
2. **Given** monitoring 成功回傳且 `warnings` 為空陣列, **When** 渲染, **Then** 才可呈現「目前沒有需要注意的事」
3. **Given** 警示卡片為 `ASSIGNED_SEAT_IDLE`, **When** 渲染, **Then** MUST 一併顯示時間資訊（任務建立至今經過多久 / 閾值 24 小時），滿足 002 spec AS3
4. **Given** 警示卡片為 `NO_RECORDS_NEAR_DUE`, **When** 渲染, **Then** MUST 一併顯示截止時間或剩餘時間（`dueDate` 已在 props 中，目前未渲染）
5. **Given** dashboard（`/teacher`）同樣消費異常資料, **When** 其 fetch 失敗, **Then** 異常統計數字 MUST NOT 顯示為 0；MUST 與班級狀況 tab 採一致的無法確認呈現
6. **Given** 老師處於離線狀態, **When** 開啟班級狀況 tab, **Then** 比照 AS1 呈現無法確認，並說明是**連線問題**；此文案 MUST 與「伺服器錯誤」的文案**區分**（兩種成因兩種文案）
7. **Given** 學生端遇到伺服器錯誤（500 等）, **When** 顯示錯誤, **Then** 文案 MUST 為「網頁出現問題」語意，MUST NOT 沿用成人化的「請稍後再試」；此為學生端伺服器錯誤的統一用語

### User Story 3 - 登記當下存不存得起來，學生要知道 (Priority: P2)

小老師在登記頁的每一個操作（勾選繳交、填成績、標記完成）目前在失敗時都是靜默的：`persist()` 遇到 `{ok:false}` 直接 return、`handleMarkComplete` 的失敗分支只 `console.error`、`saveOfflineData` 寫入失敗時連畫面更新都不觸發。而 `messages.record.saveFailed`（「沒存到！可能是網路斷掉了…」）早已寫好卻從未被引用。

**Why this priority**: 對應 vision 第 2 節「按了送出沒反應，原來沒網路 → 系統有外部依賴，操作不一定立即生效」這個學習時機。目前學生按了沒反應，但畫面也沒說明，他學到的不是「系統有外部依賴」，而是「這個 App 怪怪的」。另外「標記完成」是 vision 第 7 節的承諾動作，按下去沒反應等於承諾落空，並直接踩到「不能在同學面前卡住」的社交風險。

**Independent Test**: 登記頁勾選任一學生 → 模擬 `queueRecordUpdate` 失敗 → MUST 顯示 `record.saveFailed`；按「我登記完了」→ 模擬 API 回 500 → MUST 顯示失敗回饋且按鈕回到可再按狀態；於無痕模式或塞爆 localStorage 後操作 → MUST 顯示存不下來的提示並指向找老師。

**Acceptance Scenarios**:

1. **Given** `queueRecordUpdate` 回傳 `{ok:false}`, **When** `persist()` 處理, **Then** MUST 顯示 `messages.record.saveFailed`（接上既有 dead string），MUST NOT 靜默 return
2. **Given** 學生按下「我登記完了」且 API 回傳非 2xx, **When** `handleMarkComplete` 處理, **Then** MUST 顯示失敗回饋，且按鈕 MUST 回到可再次按下的狀態（不得停在無回應狀態）
3. **Given** 學生按下「我登記完了」且請求拋錯（斷線）, **When** catch 觸發, **Then** 比照 AS2 顯示回饋，文案 MUST 區分「沒網路」與「其他錯誤」【文案待定稿】
4. **Given** `localStorage.setItem` 拋錯（無痕模式 / 配額不足）, **When** `saveOfflineData` catch, **Then** MUST 向上傳遞失敗訊號（不得僅 `console.error` 後 return），且 MUST 顯示提示告知資料存不下來 + 指向找老師
5. **Given** AS4 之提示顯示中, **When** 學生繼續操作, **Then** 系統 MUST NOT 阻擋操作（維持 vision「不剝奪承擔後果的機會」），但提示 MUST 持續可見直到問題解除
6. **Given** 成績欄位輸入非數字, **When** 現有 `GradeRow` 驗證觸發, **Then** 維持既有 `record.numberOnly` / `gradeRange` 行為不變（此處已符合設計，本 US 不改動）

### User Story 4 - 監視器：紀錄留痕與查閱 (Priority: P3)

`Record` 目前以 `upsert` 寫入、直接覆蓋前值，因此「某筆紀錄被別人改過」在系統中不留任何痕跡。本 US 建立**門禁紀錄等級**的留痕：記錄「被誰改的、何時改的、改了哪一筆」，讓老師在起疑時有證據可查；並在學生端以陳述句讓覆蓋行為可見。

**留痕深度的決策與代價**（2026-07-20 討論定案）：採**順序處理者名單**——保留每一次處理的（座號, 時間），依發生順序排列，讓老師能看出「這筆被哪些座號、依什麼順序、在什麼時間處理過」。**仍不保留變更前的值**：老師查得到「誰、何時、第幾手」，但查不到「每一手把它改成什麼」。查得到人與經手順序，查不到內容。

此深度落在「first+last 兩座號」與「完整 audit log（含前值）」之間：比前者多了完整經手鏈與中間修改者（不再遺失），比後者少了每次變更的值。若日後發現「知道誰動過但不知道改成什麼」不足以支撐判斷，才升級為保留前值（完整 audit log）——此升級仍在 `open-questions.md` 待決。

**Why this priority**: 對應 vision 原則一 —— 覆蓋他人紀錄目前是**不可逆操作卻無任何保護**（既沒硬性防堵、也沒有還原機制），這是規則違反而非功能缺口。同時對應原則二對圍欄的定義：違規行為要可見、可補救。列 P3 而非 P1，是因為它是幾個 US 中唯一需要 schema 變更的，且傷害屬「事後查不到」而非「當下資料遺失」。

**但排序有一個反向論點需納入評估**：資料模型改動越晚做，累積的既有紀錄越多、migration 越痛，且**舊紀錄永遠補不回門禁資訊**。若團隊評估後認為此考量優先，可將本 US 提前。

**Independent Test**: 8 號小老師登記 5 號同學的成績 → 12 號小老師改掉同一筆 → 5 號同學（座號 5）再改一次 → 老師端任務細節頁 MUST 看得出這筆被 3 個不同座號依序處理過（8 → 12 → 5）及各自的時間 → 12 號小老師操作當下 MUST 看到陳述句說明這筆原本是 8 號登的 → 該陳述句 MUST NOT 阻擋操作、MUST NOT 需要額外點擊關閉。

**Acceptance Scenarios**:

1. **Given** 一筆 `Record` 被某座號處理（建立或修改）, **When** 系統寫入, **Then** MUST 將「（座號, 時間）」依發生順序追加到該筆的處理者名單；名單第一筆即最初建立者，最後一筆即最後修改者
2. **Given** 同一座號**連續**修改自己剛登的紀錄, **When** 系統寫入, **Then** MUST NOT 在名單追加重複的相鄰項（避免正常修正灌爆名單）；不同座號之間穿插的同座號修改仍各自記錄
3. **Given** 老師檢視任務細節頁, **When** 某筆紀錄的處理者名單含 ≥ 2 個不同座號, **Then** 該筆 MUST 有可辨識的視覺標示，且 MUST 能展開顯示**完整順序名單**（各座號 + 時間），讓老師看出誰是原作者、誰是後來的手
4. **Given** 老師檢視任務細節頁, **When** 頁面渲染, **Then** 登記者資訊的視覺重量 MUST 提升至老師能一眼掃出「這個任務由誰登的、有沒有混登、哪幾筆被不只一人動過」（現況僅小字「登記者 N 號」）
5. **Given** 小老師即將覆蓋他人登記的紀錄, **When** 他做出該操作, **Then** 系統 MUST 以**陳述句**告知這筆原本由誰登記（例：「這一筆原本是 8 號登的」）【文案待定稿】
6. **Given** AS5 之陳述句顯示, **When** 系統呈現, **Then** MUST NOT 使用警告色、MUST NOT 阻擋操作、MUST NOT 要求額外確認或點擊關閉 —— 學生可能正是受老師指示前來更正，系統不替老師做判斷
7. **Given** AS5 之陳述句顯示, **When** 系統呈現, **Then** MUST 以 toast 形式顯示於畫面右上角，800ms 後自動消失（不需使用者手動關閉、不阻斷後續操作、不持續累積）
8. **Given** 離線期間的覆蓋操作, **When** 稍後同步至伺服器, **Then** 該次處理的（座號, 時間）MUST 一併送出並依正確順序併入名單（不得因離線而遺失或錯置經手鏈）

### User Story 5 - 任務不見了要說對話 (Priority: P2)

`/helper/[roomId]/[taskId]` 目前有三種截然不同的成因共用同一句文案「找不到這個班級」：任務被老師刪除或封存、網路載入失敗、以及真的未加入班級。學生看到「找不到這個班級」會去重新掃 QRCode —— 一個完全無效的動作。

**Why this priority**: 直接違反 vision 第 2 節「錯誤訊息只寫『發生錯誤，請稍後再試』→ 學生無從判斷是網路問題、權限問題還是資料問題」這條明列的反面範例。同時錯失「截止日期到了，不能再修改 → 資料有生命週期」這個已被 vision 點名的學習時機。修正成本低但概念傳遞價值高。

**Independent Test**: 老師刪除任務 → 學生端重新整理 → MUST 顯示任務已被老師收起來（非「找不到班級」）；學生離線且無快取 → MUST 顯示連線問題（非「找不到班級」）；清空 localStorage 直接開啟 `/helper/xxx/yyy` → 才顯示未加入班級。

**Acceptance Scenarios**:

1. **Given** 任務 API 回傳 404（任務已被老師刪除）, **When** 學生端渲染, **Then** MUST 顯示指向「任務被老師收起來了、去問老師」的文案，MUST NOT 顯示 `room.notFoundTitle`【文案待定稿】
2. **Given** 任務已被封存, **When** 學生端載入, **Then** 比照 AS1 呈現，並 MUST NOT 提供「重新掃碼」這類無效行動作為主要出口
3. **Given** 載入失敗成因為網路（fetch 拋錯或離線且無快取）, **When** 渲染, **Then** MUST 顯示連線相關文案並指向「連上網路再試」，可沿用既有 `common.networkError` 語氣
4. **Given** 本機無此房間紀錄（未加入班級 / 已清除快取）, **When** 渲染, **Then** 才顯示 `room.notFoundTitle` + 重新進入入口（現有行為）
5. **Given** `/helper/[roomId]` 任務清單頁的載入失敗, **When** 渲染, **Then** MUST 比照 AS3 區分網路問題與無資料，不得沿用同一句文案
6. **Given** 任務因截止或已標記完成而鎖定, **When** 學生檢視, **Then** 維持既有 `task.lockedDuePassed` / `task.lockedCompleted` 行為不變（此處已符合設計）

### User Story 6 - 異常偵測規則重整 (Priority: P1)

現行兩條規則各自帶有前置限制（規則一要求有指定小老師、規則二要求有設截止），其交集導致**「沒指定又沒截止」的任務異常涵蓋率為零**。同時規則一混合判斷「事情有沒有推進」與「指定的那個人有沒有動」兩種關注點。本 US 重整為：規則一改判**任務層級的活動**（滑動視窗），規則二改用**絕對時鐘**（截止日當天 08:00），並將截止時間預設由 23:59:59 標準化為 17:00。

**Why this priority**: 涵蓋率為零的那一格，正是 vision 第 5 節理想場景所描述的建立方式 ——「誰負責收可以之後再指定，截止時間也可以彈性設」。**偵測空窗剛好落在產品最推薦的使用方式上**，等於老師照著理想流程走，反而最沒有保障。這使得「老師可以放心放手」在最常見的情境下不成立。

**「心跳替代方案」的設計說明**（2026-07-20 討論確立，推翻 `open-questions.md` 原結論）:

伺服器無法即時偵測「裝置離線中」—— 離線裝置不產生任何資料，缺席無法被觀測。這是原理限制。但改用滑動視窗後，「裝置離線導致資料傳不上來」會表現為「這個任務長時間沒有新資料進來」，與「學生忘記登記」共用同一個訊號。**兩者對老師而言的行動是相同的**（去看一下卡在哪裡），因此不需要區分成因即可提供價值。

本設計以**任務層級的活動時間**作為裝置心跳的代理指標，用既有資料即可運作，不需新增 Device entity。代價是無法指出「是哪一台裝置」。

**關注點分離**: 重整後，異常規則只回答「事情有沒有在推進」；「誰在動、誰覆蓋了誰」全數由 US4 的證據機制承接。原規則一同時判斷這兩件事，是把兩種關注點揉在一起 —— 這也是它需要 `assignedRecorderHasRecord` 這個輸入與 monitoring route 中額外一次 `distinct` 查詢的原因，重整後兩者皆可移除。

**Independent Test**: 建立一個無指定小老師、無截止時間的任務 → 24 小時後 MUST 出現停擺警示（現況不會）；登記 3 筆後靜置 24 小時 → MUST 再次出現停擺警示（現況不會）；全班登滿後靜置 24 小時 → MUST NOT 出現警示；建立截止日為隔天的任務並保持零登記 → 隔天 08:00 起 MUST 出現警示。

**Acceptance Scenarios**:

1. **Given** 任一 ACTIVE 且未封存的任務, **When** 距離**最後一次登記活動**已滿 24 小時, **Then** MUST 判定為停擺異常 —— **不再要求 `assignedSeatNumber != null`**
2. **Given** 任務從未有任何登記, **When** 系統計算閒置時長, **Then** 起算點 MUST 退回任務建立時間（維持現行行為）
3. **Given** 任務已有登記且之後停擺, **When** 系統計算閒置時長, **Then** 起算點 MUST 為最後一筆登記的時間（滑動視窗）—— 此即「開了頭然後停擺」的涵蓋方式
4. **Given** 任務的登記筆數已達班級學生總數（全班登滿）, **When** 系統判斷, **Then** MUST NOT 判定為停擺，即使小老師未按「我登記完了」。分子（登記筆數）與分母（學生總數）MUST 同時排除 `isRemoved` 學生（見 Edge Cases）
5. **Given** 規則一重整完成, **When** 檢視 `detectAnomalies` 的輸入, **Then** `assignedRecorderHasRecord` MUST 移除；`monitoring/route.ts` 中查詢 `isAssignedRecorder` 的 `distinct` 語句 MUST 一併移除
6. **Given** 任務有設截止日, **When** 已過**截止日當天 08:00**（`Asia/Taipei`）且全班零登記, **Then** MUST 判定為異常 —— 取代現行的「距截止 6 小時」相對閾值
7. **Given** 任務於截止日當天 08:00 **之後**才建立, **When** 系統判斷規則二, **Then** MUST NOT 觸發（避免剛建立就被喬）；該任務仍受規則一（24h 停擺）保護
8. **Given** 老師建立新任務並選定截止日, **When** 系統寫入 `dueDate`, **Then** 時間部分 MUST 為當天 **17:00**，取代現行硬編的 `23:59:59`
9. **Given** 資料庫中已存在 `dueDate` 為 23:59:59 的舊任務, **When** 本變更上線, **Then** MUST NOT 進行 migration；舊任務維持原截止時間（接受一段期間的新舊不一致）
10. **Given** 截止時間預設改為 17:00, **When** `getTaskLockReason` 判斷鎖定, **Then** 新任務 MUST 於當天 17:00 鎖定 —— 此為**實質行為變更**（學生可登記時間由半夜縮短至放學），非僅警示調整

### User Story 7 - 標記完成前，先照一次現實 (Priority: P3)

小老師按下「我登記完了」（標記 `HELPER_COMPLETED`）是 vision 第 7 節的**承諾動作**。但目前這個承諾不與現實核對：小老師只登了 5/30 就按完成（誤按、以為只需登指定的幾個、或想早點結束），系統照收，老師端沒有任何訊號。更關鍵的是，異常規則的共同前提是「僅 `status === 'ACTIVE'` 才判」—— **任務一進入 `HELPER_COMPLETED`，規則一、規則二全部停判**（見 `specs/anomaly-rules.md`「共同前提」）。系統在承諾發生的那一刻，剛好停止查看。

本 US 在承諾送出前補一道**學生端的現實核對**：若登記筆數未達班級人數，先用陳述句讓小老師看見落差（「還有 N 個同學沒登記」），再讓他自己決定是否繼續。

**為何選在學生端、而非老師端補**：同一個盲區可以做成老師端警示（標記完成後登記不足就示警），但那會多一條頻繁觸發的警示、把老師推回主動監控者，且在繳交類任務上假陽性（見 Edge Cases）。做成學生端的承諾確認，是把檢查下推到承諾的人身上（vision 原則二「能不能改由學生做」），零老師負擔，且正好命中 vision 第 2 節「資料有生命週期」的學習時機 —— 標記完成＝鎖定，鎖了要找老師才能開。這也呼應第 7 節承諾裝置：把承諾與可見的現實擺在一起，聲明才有重量。

**Why this priority**: 對應承諾裝置 —— 承諾若無人核對，效力大幅下降（vision 第 7 節註腳）。現行設計讓系統在承諾當下轉為全盲，正是承諾裝置最不該出現的空窗。列 P3 而非更高，因為它**不涉及資料遺失**（不同於 US1）也**不謊報平安**（不同於 US2），且純學生端、無 schema 變更、成本低；傷害屬「假承諾誤導老師」，並可由老師事後在任務細節頁的完成度資訊補救。

**與「一律彈確認」反例的區分**：vision 原則一明列「對所有操作一律彈確認視窗 → 學生會習慣性略過」為反面範例。本提示**只在有落差時出現**（登滿即直接完成、不打擾），且指向概念（你的登記還沒滿、完成＝鎖定）而非只指向行動，因此不落入該反例。

**Independent Test**: 建立成績類任務、班級 30 人 → 小老師登記 20 人後按「我登記完了」→ MUST 出現陳述句說明「還有 10 個同學沒登記、完成後就不能自己改」＋兩條出路（繼續完成 / 回去補登）→ 選「繼續完成」→ 任務照常進入 `HELPER_COMPLETED`；另一任務登滿 30 人後按完成 → MUST NOT 出現提示，直接完成；繳交類任務登記未滿後按完成 → MUST NOT 出現提示。

**Acceptance Scenarios**:

1. **Given** 成績類任務且登記筆數 < 班級學生總數（兩者皆排除 `isRemoved`）, **When** 小老師按「我登記完了」, **Then** 系統 MUST 先顯示承諾確認提示，MUST NOT 直接送出 `HELPER_COMPLETED`
2. **Given** 承諾確認提示顯示, **When** 系統呈現, **Then** MUST 以陳述句指出尚有 N 位同學未登記，並說明標記完成後將鎖定、需找老師才能重開（指向概念，非僅指向行動）【文案待定稿】
3. **Given** 承諾確認提示顯示, **When** 小老師選擇「繼續標記完成」, **Then** 系統 MUST 照常送出 `HELPER_COMPLETED`（不剝奪承擔後果的機會 —— vision 原則一：可逆操作只提示後果，標記完成可由老師重開）
4. **Given** 承諾確認提示顯示, **When** 小老師選擇「先回去補登」, **Then** MUST 返回登記畫面、MUST NOT 送出完成，且不留下任何鎖定
5. **Given** 登記筆數已達班級學生總數（全班登滿）, **When** 小老師按「我登記完了」, **Then** MUST NOT 顯示提示，直接完成（避免「一律彈確認」反例）
6. **Given** 繳交類任務, **When** 小老師按「我登記完了」, **Then** MUST NOT 觸發此提示 —— 「未繳交不存記錄」使「未登記」與「已確認未交」無法區分，count-based 提示在繳交類無意義（沿用既有假陽性決議，見 Edge Cases）
7. **Given** 小老師離線、登記率以本機快取推算, **When** 提示判斷, **Then** 以本機可見資料為準即可（提示為提醒非強制）；快取不準 MUST NOT 阻擋標記完成

### User Story 8 - 完成但登記太少，要提醒老師 (Priority: P2)

US7 在小老師按「我登記完了」的當下輕推一次，但那是**可以被略過**的提示 —— 小老師選「繼續完成」就過了。若他真的誤觸、或沒登完就謊報完成，任務會停在 `HELPER_COMPLETED`，而異常規則的共同前提是「只判 ACTIVE」，於是**所有規則對它停判、老師端零偵測**。本 US 新增一條專判 `HELPER_COMPLETED` 的異常（`specs/anomaly-rules.md` 規則三）：標記完成時登記率 < 50% 即升為老師端警示，讓老師趕在截止前介入。

**與 US7 的分工（兩個閾值）**：US7 是學生端提示（任何不足即輕推、不動老師）；US8 是老師端警示（只在明顯不足 < 50% 才升級）。同一件事按受眾分兩個閾值。

**繳交類這次納入（與 US7 相反）**：US7 FR-118 排除繳交類，因為它測「處理進度」，而繳交類的「未處理」與「已確認未交」不可分。但 US8 測的是**繳交率本身過低**，不論成因（真的很多人沒交／小老師謊報）老師的行動都相同（趕快去了解、催、延長截止、reopen）。既然不需區分成因即可行動，繳交類就納入 —— 此邏輯與規則一「停擺 vs 離線共用同一訊號」一致。

**Why this priority**: 這是承諾裝置的安全網 —— US7 的輕推可被略過，US8 是略過之後唯一還會被接住的地方。它有時效性：標記完成通常早於截止 17:00，此刻提醒老師還來得及補救，錯過就鎖定了。列 P2 而非 P1：不涉及資料遺失，傷害屬「假承諾晚一點被發現」而非「當下資料消失」。

**Independent Test**: 成績類任務、班級 30 人 → 小老師登記 10 人（33%）後按「我登記完了」→ 老師端班級狀況 tab MUST 出現該任務的異常卡片 → 點進任務詳情 MUST 看到完成度資訊（已登記 10/30、未登記清單）；另一任務登記 20 人（67%）後標記完成 → MUST NOT 出現異常；繳交類任務全班 30 人只有 8 人繳交後標記完成 → MUST 出現異常（繳交類同樣納入）。

**Acceptance Scenarios**:

1. **Given** 任務 `status === 'HELPER_COMPLETED'` 且登記率 < 50%（分子分母皆排除 `isRemoved`）, **When** `detectAnomalies` 判斷, **Then** MUST 判定為異常 —— 不論成績類或繳交類
2. **Given** 任務 `status === 'HELPER_COMPLETED'` 且登記率 ≥ 50%, **When** 判斷, **Then** MUST NOT 判定為異常
3. **Given** 任務仍為 `ACTIVE`（未標記完成）, **When** 判斷規則三, **Then** MUST NOT 觸發 —— 規則三只判 `HELPER_COMPLETED`，`ACTIVE` 任務由規則一、二涵蓋
4. **Given** 班級學生（未移除）總數為 0, **When** 計算登記率, **Then** MUST NOT 判定為異常（避免除以零）
5. **Given** 規則三觸發的異常卡片, **When** 老師端渲染, **Then** MUST 顯示登記率與班級人數（例：已登記 10/30），並提供一鍵進到任務詳情看未登記清單的入口【文案待定稿】
6. **Given** `detectAnomalies` 現行對 `status !== 'ACTIVE'` 直接 early-return, **When** 實作規則三, **Then** MUST 調整為：規則一、二維持 ACTIVE-only、規則三獨立判 `HELPER_COMPLETED`；`monitoring` 與 dashboard 兩個 endpoint MUST 一併把 `HELPER_COMPLETED` 任務納入查詢範圍（現行可能只撈 ACTIVE）
7. **Given** 老師據規則三點進任務、判斷是誤觸或謊報, **When** 老師處理, **Then** 沿用既有動作（`reopen` 重新開放 / `extendDue` 延長截止 / `close` 結案），本 US 不新增老師端操作

> 規則三的完整定義（觸發、閾值、繳交類納入理由、已知限制）以 `specs/anomaly-rules.md` 為單一真實來源；本 US 僅描述行為與驗收。

### Edge Cases

- **失敗態與離線態同時存在**：學生離線 + 佇列中已有不可重試的衝突項目。兩種狀態的視覺優先順序需定義，避免兩個 banner 疊在一起把畫面塞滿（參照 003 FR-070 已遇過的「色塊相疊互相干擾」問題）
- **無痕模式 / localStorage 不可持久化**：**決議 —— 本 feature 不特別處理無痕模式。** 佇列無法跨 session 持久化屬瀏覽器環境限制，非本產品的目標情境。若無痕模式下 `localStorage.setItem` 直接拋錯，仍由 US3 FR-089 / FR-090 的通用「存不下來 → 去找老師」提示接住（不會靜默壞掉）；但「關閉無痕視窗後資料遺失」不在本 feature 的保護範圍
- **重試耗盡 / 不可重試後老師重新開放任務**：**決議 —— 每次頁面載入時重置重試判定並重試一次。** 頁面重新整理 MUST 重置佇列中操作的 `retryCount` 與不可重試標記，並重新嘗試同步一次；**佇列項目（未送出的資料）本身仍持久化、不清除**。因此老師重新開放任務後，學生只要重新整理頁面即可讓原本卡住的登記重新送出，**無需重新登記**；若重試後仍失敗（例如任務仍鎖定），失敗態重新出現。此設計呼應 003 `useFailureCounter`「重整即重置」的模式，關鍵差異是：此處重置的只是重試判定，未送出的資料一律保留
- **同一筆紀錄被覆蓋多次**：**已由 US4 順序處理者名單解決** —— 完整經手鏈（含中間修改者）依序保留，不再只剩最後一手。仍未保留的是「每一手改成什麼值」（前值），該升級（完整 audit log）留在 `open-questions.md`
- **老師端無法確認狀態下的異常統計**：dashboard 的「異常」數字在無法確認時應顯示什麼（`—`？上次成功的值 + 時間戳？）
- **停擺判定與班級人數變動**：**決議 —— 計算層排除，不刪資料。** 異常與統計的計算 MUST 同時排除 `isRemoved` 學生：分母（學生總數）只算未移除者，分子（登記筆數）不計移除學生的紀錄。records 實體一律保留，不因移除而刪除 —— 因此 002 FR-025（歷史紀錄保留）與 FR-026（還原）不受影響，也不違反 vision 原則一（移除維持可逆）。此決議否決了「移除即刪 records」的方向：統計輸出與刪除相同，但保住了可還原性

- **繳交類任務的停擺假陽性（已知並接受）**：`src/lib/task.ts` 的設計是「未繳交」不存 `NOT_SUBMITTED`，而由「查無記錄」推導。因此**系統無法區分「小老師還沒動」與「小老師跑完一輪、答案是沒人交」** —— 兩者在資料上都是零筆 Record。後果：

  - 規則二（截止日 08:00 零登記）會對「全班確實都沒交」的任務誤報
  - US6 的滑動視窗因無活動時間戳而退回 `createdAt`，24 小時後誤判停擺
  - US6 AS4 的「登滿全班就不判」保護，在繳交類任務上只要有人沒交就達不到，等同失效

  此為 001 資料模型選擇一路帶下來的限制，非本 feature 引入，但 US6 擴大偵測範圍後會讓它從邊角案例變得較常見。**經 2026-07-20 討論決定接受此假陽性**，不改資料模型、不新增活動訊號 —— 理由是「全班都沒交」在實務上罕見，且老師點進任務即可辨識。若實際使用中誤報頻繁，優先考慮的解法是讓「已確認未繳交」也存一筆記錄（根治），而非在異常規則上加特例
- **截止日當天是假日 / 停課**：規則二在截止日當天 08:00 起算，若當天全校停課，警示會在無人能處理的時間點出現。資料模型無學校行事曆，暫不處理
- **17:00 鎖定與延長截止的互動**：**決議 —— 延長截止的新截止時間同樣標準化為 17:00。** 老師使用既有「延長截止」功能設定新日期時，時間部分 MUST 比照 FR-108 補為當天 17:00，保持全站截止時間語意一致（見 FR-108）
- **封存任務接受離線寫入後的呈現**：**決議 —— 照常寫入；老師端證據級標示，學生端算成功但告知遲交。** 沿用 002 L232 接受寫入。**老師端**：像其他監視器行為一樣把「這筆是任務封存後才進來的」標示出來（證據級、被動可見，不主動喊）。**學生端**：該次同步**視為成功**（非衝突、不擋），但回饋訊息告知「這個任務老師已經收起來了」（用「已收起 / 已封存」而非「遲交」—— 封存未必等於超過截止），對應 vision「資料有生命週期」的學習時機。【具體字句待定稿】
- **標記完成前承諾核對的適用範圍（US7）**：僅適用**成績類**任務。繳交類因「未繳交不存記錄」，「未登記」與「已確認未交」在資料上不可區分，count-based 的落差提示會假陽性（與 US6 繳交類假陽性同源）。故繳交類 MUST NOT 觸發此提示。若日後要涵蓋繳交類，前提是「已確認未繳交」也存一筆記錄 —— 與 US6 假陽性的根治解法相同
- **承諾核對的「登滿」定義與部分登記任務**：US7 沿用 US6 AS4 的「登滿＝每位未移除學生各有一筆記錄」假設。若某成績類任務本就只需登部分學生（如補考三人），此提示會對「正常的部分登記」誤觸 —— 與 US6「登滿就不判」的假設同一個弱點。**決議：接受此限制**，不為 US7 單獨引入「本任務不需全班登記」的欄位；若早期回饋顯示部分登記任務常見，US6 / US7 一併重新評估
- **承諾確認提示與離線**：登記率以學生端本機可見資料推算，離線時可能過期。提示為提醒非強制，MUST NOT 因快取不準而阻擋標記完成（見 US7 AS7）
- **規則三與繳交類的低繳交誤報（已知並接受）**：固定 50% 對「本來就低繳交」的項目（自願性同意書等）會誤報。**決議：接受**（2026-07-21），不引入班級基準法（需歷史資料、難向老師解釋）；老師點進任務即可辨識，且低繳交本身多半也值得老師知道。詳見 `anomaly-rules.md` 規則三「已知限制」
- **規則三與 CLOSED**：老師結案（`CLOSED`）後 MUST NOT 再判規則三 —— 老師已親自處理過等於已介入，再喊無意義。規則三只判 `HELPER_COMPLETED`，此點自然成立
- **US7 略過後由 US8 接住**：小老師在 US7 提示選「繼續完成」（登記率 < 100%）→ 若登記率同時 < 50%，US8 規則三 MUST 在老師端接住；若在 50% ~ 100% 之間，則不升為老師警示（兩閾值的中間地帶刻意留白，交由老師主動查看完成度資訊）

## Requirements _(mandatory)_

> 標籤說明：**【補機制】** 代表必須先實作偵測或錯誤捕捉；**【補文案】** 代表機制已存在，補上使用者可見的回饋即可。

### Functional Requirements

**US1 — 同步失敗出口**

- **FR-077**【補機制】: `processSyncQueue` MUST 解析 `/api/sync` 回傳的 `conflicts` 欄位（207 與 409 皆是），MUST NOT 僅讀取 `operationIds`
- **FR-078**【補機制】: 系統 MUST 將同步失敗分類為**可重試**（網路層失敗）與**不可重試**（任務已鎖定、找不到任務、資料驗證失敗）；不可重試者 MUST 立即停止重試。分類 MUST 依 FR-112 的錯誤碼進行，MUST NOT 以錯誤訊息的中文文字比對
- **FR-079**【補機制】: 重試次數達上限或判定不可重試的操作 MUST NOT 從佇列靜默濾除；MUST 保留並標記狀態，供 UI 呈現。重試判定（`retryCount` 與不可重試標記）為 session 範圍，MUST 於頁面載入時重置並觸發一次重試 —— 支援老師重新開放任務後的自動恢復（見 Edge Cases）；未送出的佇列資料不受此重置影響，一律保留
- **FR-080**: 重試策略已定調（2026-07-20）—— 因 FR-079 的「每次頁面載入重置並重試」，session 內「放棄」不再等於資料死亡，只是延到下次載入。因此重試機制的角色是「避免 session 內狂打伺服器」，而非「決定資料生死」。具體退避曲線與 session 內上限屬無關痛癢的調參，交由 plan.md 定，不影響資料安全
- **FR-081**【補文案】: `SyncIndicator` MUST 新增**失敗態**，與「同步中」「待上傳」在視覺上可區分，並顯示受影響筆數
- **FR-082**【補文案】: 失敗態文案 MUST 指向「去找老師」（沿用 003 FR-065 已建立的「連續失敗即升級為找老師」模式），MUST NOT 僅顯示技術原因

**US2 — 老師端誠實呈現**

- **FR-083**【補機制】: 老師端 MUST 區分「已確認無異常」與「無法確認」兩種狀態；monitoring 請求失敗時 MUST NOT 落入前者
- **FR-084**【補文案】: 無法確認狀態 MUST 提供重試入口，且 MUST 區分「連線問題（老師自己沒網路）」與「伺服器錯誤」兩種文案
- **FR-085**【補文案】: 警示卡片 MUST 顯示時間或閾值資訊（`ASSIGNED_SEAT_IDLE` 顯示已閒置時長；`NO_RECORDS_NEAR_DUE` 顯示截止或剩餘時間）—— 補齊 002 spec AS3 既有要求
- **FR-086**【補機制】: dashboard 的異常統計數字在資料無法取得時 MUST NOT 呈現為 0，MUST 顯示 **`—`**（代表未知），MUST NOT 顯示上次成功的過期值（避免老師誤信過期數字，違反 vision 第 6 節「被通知後的決策者」）

**US3 — 學生端存檔回饋**

- **FR-087**【補文案】: `persist()` 於 `queueRecordUpdate` 失敗時 MUST 顯示 `messages.record.saveFailed`（既有 dead string 接線）
- **FR-088**【補文案】: `handleMarkComplete` 於非 2xx 或拋錯時 MUST 顯示失敗回饋，按鈕 MUST 回復可再次操作狀態
- **FR-089**【補機制】: `saveOfflineData` 於 `localStorage.setItem` 失敗時 MUST 向上傳遞失敗訊號，MUST NOT 僅 `console.error` 後 return
- **FR-090**【補文案】: 本機儲存失敗 MUST 顯示提示，說明資料存不下來並指向找老師（對應 vision「資料存在本機」概念）
- **FR-091**: 上述所有失敗提示 MUST NOT 阻擋學生繼續操作（vision 原則：不剝奪承擔後果的機會）

**US4 — 監視器留痕與查閱**

- **FR-092**【補機制】: `Record` MUST 保留一份**順序處理者名單** —— 每次處理（建立或修改）追加一筆（座號, 時間），依發生順序排列。名單第一筆＝最初建立者、最後一筆＝最後修改者。**不保留變更前的值**
- **FR-093**【補機制】: 同一座號**連續**修改自己剛登的紀錄 MUST NOT 在名單追加相鄰重複項（避免正常修正灌爆名單）；被其他座號穿插後的同座號再次修改仍各自記錄
- **FR-094**【補文案】: 老師端任務細節頁 MUST 對名單含 ≥ 2 個不同座號的紀錄提供可辨識標示，並 MUST 能展開顯示完整順序名單（各座號 + 時間）
- **FR-095**【補文案】: 老師端任務細節頁的登記者資訊視覺重量 MUST 提升至可一眼辨識「誰登的、有無混登、哪幾筆被不只一人動過」
- **FR-096**【補文案】: 學生覆蓋他人紀錄時 MUST 以陳述句告知原登記者（名單第一筆）；呈現形式為**右上角 toast、800ms 自動消失**；MUST NOT 使用警告色、MUST NOT 阻擋、MUST NOT 要求確認或手動關閉
- **FR-097**【補機制】: 離線期間產生的處理紀錄（座號, 時間）MUST 隨同步一併送出並依正確順序併入名單
- **FR-097a**【補文案】: 封存後才同步進來的登記，老師端 MUST 以證據級標示（被動可見、不主動喊），讓老師能看出「這筆是任務封存後才進來的」；沿用 002 L232「接受寫入」不變

**US5 — 生命週期語意修正**

- **FR-098**【補文案】: 任務 404 / 已封存 MUST 顯示指向「任務被老師收起來」的文案，MUST NOT 沿用 `room.notFoundTitle`
- **FR-099**【補文案】: 載入失敗成因為網路時 MUST 顯示連線相關文案，與「資料不存在」明確區分
- **FR-100**【補文案】: `room.notFoundTitle` MUST 僅用於「本機無此房間紀錄」之情境
- **FR-101**【補文案】: `/helper/[roomId]` 任務清單頁 MUST 比照 FR-098 ~ FR-100 區分成因
- **FR-101a**【補文案】: 離線登記於同步時發現任務已封存者，學生端 MUST 視為**成功**（非衝突、不擋），並以生命週期文案告知「這個任務老師已經收起來了」（用「已收起 / 已封存」而非「遲交」—— 封存未必等於超過截止；對應 vision「資料有生命週期」）【文案待定稿】

**US6 — 異常偵測規則重整**

- **FR-102**【補機制】: 規則一 MUST 改判**任務層級活動**，移除 `assignedSeatNumber != null` 前置條件；閒置時長 MUST 自**最後一次登記活動**起算，無任何登記時退回任務建立時間（滑動視窗）
- **FR-103**: 規則一閾值 MUST 維持 24 小時（與現行對齊，便於向老師解釋）
- **FR-104**【補機制】: 登記筆數已達班級學生總數的任務 MUST NOT 判定為停擺；`detectAnomalies` MUST 新增班級學生總數作為輸入。學生總數（分母）MUST 只計 `isRemoved=false` 的學生；登記筆數（分子）MUST 排除移除學生的紀錄。records 實體不因移除而刪除（保住 002 FR-025 / FR-026）
- **FR-105**: `detectAnomalies` 的 `assignedRecorderHasRecord` 輸入 MUST 移除；`monitoring/route.ts` 中對應的 `distinct` 查詢 MUST 一併移除
- **FR-106**【補機制】: 規則二 MUST 改用絕對時鐘 —— 截止日當天 **08:00**（`Asia/Taipei`）起，全班零登記即判異常，取代「距截止 6 小時」
- **FR-107**: 規則二 MUST 僅適用於截止日當天 08:00 **之前**已建立的任務
- **FR-108**【補機制】: 新建任務的 `dueDate` 時間部分 MUST 為當天 **17:00**（取代 `TaskForm.tsx` 硬編的 `23:59:59`）。既有「延長截止」功能設定的新截止日 MUST 同樣標準化為當天 17:00，保持語意一致
- **FR-109**: 既有 `dueDate` 為 23:59:59 的任務 MUST NOT 進行 migration
- **FR-110**【補文案】: 兩條規則的文案 MUST 隨語意調整 —— `anomalyAssignedSeatIdle`（現為「指定座號 N 已超過 24 小時沒有登記」）MUST 改為描述任務停擺而非特定座號【文案待定稿】

**跨 US — API 錯誤碼統一（US1 / US3 的功能前提，非獨立 US）**

> 原列為技術債，複審後改判為功能前提：US1 的衝突分類（FR-078）與 US3 的存檔失敗回饋（FR-087）都需要 client 端能可靠辨識 server 回傳的錯誤，而非比對中文字串。因此隨本 feature 一併修正，不延後。

- **FR-111**【補機制】: `/api/sync` 與 `/api/records` 的所有錯誤回應 MUST 改走 `ERROR_CODES`（`src/i18n/errorCodes.ts`），MUST NOT 回傳硬編中文字串（含 `conflicts[].reason`、`errors[].reason` 與各 400 / 404 / 500 的 `error` 欄位）
- **FR-112**【補機制】: `/api/sync` 回傳的 `conflicts[].reason`（及 `/api/records` 的 `errors[].reason`）MUST 為 `ERROR_CODES` 碼值，供 FR-078 分類使用；「任務已鎖定」「找不到任務」「資料驗證失敗」等 MUST 各有可辨識的碼
- **FR-113**【補文案】: 會傳達到學生的錯誤碼 MUST 在 messages 字典中有兒童語氣對應文案（`resolveError()` 可解析）；純內部錯誤（如 500）沿用既有 catch-all `common.error`，不需個別文案

**US7 — 標記完成前的承諾核對**

- **FR-114**【補機制】: 小老師按「我登記完了」時，系統 MUST 先比對登記筆數與班級學生總數（兩者皆排除 `isRemoved`）；成績類任務且未達班級人數時 MUST 先顯示承諾確認提示，MUST NOT 直接送出 `HELPER_COMPLETED`
- **FR-115**【補文案】: 承諾確認提示 MUST 以陳述句指出尚有 N 位同學未登記，並說明標記完成後將鎖定、需找老師重開（指向概念，對應 vision「資料有生命週期」）【文案待定稿】
- **FR-116**: 承諾確認提示 MUST 提供兩條出路 ——「繼續標記完成」與「先回去補登」。選前者 MUST 照常送出 `HELPER_COMPLETED`（不剝奪承擔後果）；選後者 MUST 返回登記畫面且不留下鎖定。MUST NOT 硬性阻擋完成（vision 原則一：可逆操作只提示後果 —— 標記完成可由老師重開）
- **FR-117**: 登記筆數已達班級學生總數時 MUST NOT 顯示提示，直接完成 —— 避免 vision 原則一「一律彈確認」反例
- **FR-118**: 繳交類任務 MUST NOT 觸發此提示；成因與 US6 繳交類假陽性相同（未繳交不存記錄，無法區分「未登記」與「已確認未交」）。若未來要涵蓋，前提為「已確認未繳交」也存一筆記錄
- **FR-119**: 登記筆數與班級學生總數的計算 MUST 沿用 US6 FR-104 已定的口徑（分母只計 `isRemoved=false` 學生、分子排除移除學生的紀錄），MUST NOT 另立第二套統計邏輯

**US8 — 完成但登記率過低（老師端警示）**

- **FR-120**【補機制】: 新增異常規則三 —— 任務 `status === 'HELPER_COMPLETED'` 且登記率 < 50% 時 MUST 判定為異常。登記率口徑沿用 FR-104 / FR-119（分子分母皆排除 `isRemoved`；繳交類分子為 SUBMITTED 筆數＝繳交率）
- **FR-121**【補機制】: 規則三 MUST 同時適用成績類與繳交類（**與規則一、二排除繳交類相反**）；理由見 `specs/anomaly-rules.md` 規則三「為什麼繳交類不排除」——測的是繳交率過低而非處理進度，不論成因老師行動相同
- **FR-122**【補機制】: `detectAnomalies` 現行對 `status !== 'ACTIVE'` 的 early-return（`anomalyDetection.ts:43`）MUST 調整 —— 規則一、二維持 ACTIVE-only，規則三獨立判 `HELPER_COMPLETED`；`monitoring/route.ts` 與 dashboard endpoint MUST 把 `HELPER_COMPLETED` 任務納入查詢範圍（現行可能只撈 ACTIVE）
- **FR-123**: 班級學生（未移除）總數為 0 時 MUST NOT 判定規則三異常（避免除以零）
- **FR-124**【補文案】: 規則三的異常卡片 MUST 顯示登記率與班級人數（例：已登記 10/30），並提供進入任務詳情的入口；文案 MUST 描述「完成但登記偏少」，MUST NOT 沿用停擺或截止的語意【文案待定稿】
- **FR-125**: 規則三閾值 50% 為待觀察調整的參數（如同規則一的 24 小時）。若上線後過吵，優先調整閾值或改用班級基準法，MUST NOT 直接移除規則三 —— 否則 `HELPER_COMPLETED` 空窗重現

### Non-Functional Requirements

- **NFR-011**: 所有新增使用者可見文字 MUST 集中於 `src/messages/`，元件內不得硬寫字串（沿用 NFR-001）
- **NFR-012**: 學生端所有新增文案 MUST 使用兒童語氣，並 MUST 指向具體下一步（沿用 003 的「不讓學生在不知道下一步的狀況下卡住」子原則）
- **NFR-013**: **未送出的資料**（佇列項目）MUST 持久化於 localStorage，重整不得清除 —— 這是資料安全底線。但**重試判定**（`retryCount` 與不可重試標記）MUST NOT 持久化，MUST 於每次頁面載入時重置並重新嘗試一次（見 US1 AS7 / FR-079 / Edge Cases）。重試判定的處理方式與 003 NFR-010 的失敗計數一致（刻意不持久化），差別在於底層資料一律保留
- **NFR-014**: 處理者名單的儲存 MUST 讓既有紀錄 migration 不失敗；既有紀錄無歷史名單，視為不可考（可用「僅含現有 `recorderSeatNumber` 一筆、時間為 `createdAt`」的最小名單回填，或留空由 UI 呈現「無歷史」）
- **NFR-015**: `detectAnomalies` MUST 維持純函式（無 I/O），供 monitoring 與 dashboard 兩個 endpoint 共用，確保兩處判斷一致
- **NFR-016**: 規則二引入絕對時鐘後，時區 MUST 明確為 `Asia/Taipei`，MUST NOT 依賴伺服器本地時區（Cloudflare Workers 執行環境為 UTC）

### Key Entities (delta only)

**RecordHandler**（新增子表）— 承載**順序處理者名單**。決議採子表（2026-07-20）：查詢乾淨、可索引，優於 JSON 陣列欄位。每筆代表一次處理：

- `recordId`（FK → Record）
- `seatNumber`（該次處理者座號）
- `handledAt`（該次處理時間）
- 順序由 `handledAt` 決定；`Record` 1:N `RecordHandler`

**Record**（既有）與名單的關係（**避免重複造欄位**）：

- `recorderSeatNumber`（現值）＝名單**最後一筆**的座號（最後修改者）—— 保留作為便捷欄位，不另立「最後修改者座號」
- `updatedAt`（`@updatedAt`）＝名單最後一筆的時間 —— 不另立「最後修改時間」
- 名單**第一筆**＝最初建立者 —— 因此不需要先前討論過的獨立「最初建立者座號」純量欄位
- `isAssignedRecorder`：US6 FR-105 移除其在**異常偵測**的用途，但仍為證據顯示所需，**不得刪除欄位**；其語意為「最後一手是否為指定小老師」（跟隨 `recorderSeatNumber`）—— **維持現狀**（2026-07-20 決議），老師端顯示沿用此語意，不改指向名單首筆

**Task**（既有）— 無 schema 變更，但 `dueDate` 的**寫入慣例**變更：由 `T23:59:59` 改為 `T17:00`（US6 FR-108）。此變更影響 `getTaskLockReason` 的實際鎖定時點，屬行為變更。

**detectAnomalies 輸入介面**（非 entity，但為跨 endpoint 契約）：新增班級學生總數（只計 `isRemoved=false`）、最後一次登記活動時間；移除 `assignedRecorderHasRecord`。

> **實作注意**：monitoring route 目前用 `task._count.records`（原始筆數，含移除學生的紀錄）當 `recordedCount`。FR-104 要求分子排除移除學生，因此此處 MUST 改為過濾後的計數（例如 `_count` 加 `where: { student: { isRemoved: false } }`），dashboard endpoint 同理。純函式 `detectAnomalies` 本身不查 DB，兩個 endpoint 都要負責傳入已過濾的數值。

**無新增 entity。** 其餘 US（1、2、3、5、7、8）為純 UI / 流程 / 錯誤處理層改動。US7、US8 皆不新增任何欄位：US7 在 `handleMarkComplete` 送出前讀取既有的登記筆數與班級人數做比對；US8 在 `detectAnomalies` 沿用同一組輸入（班級學生總數、登記筆數、`task.status`／`task.type`），僅要求 endpoint 把 `HELPER_COMPLETED` 任務也傳入（FR-122）。

## Success Criteria _(mandatory)_

- **SC-019**: 學生的登記在任何情境下都不會靜默消失 —— 程式碼中 MUST NOT 存在「從同步佇列移除但未通知使用者」的路徑
- **SC-020**: 老師端在資料無法取得時，畫面 MUST NOT 出現任何形式的「一切正常」表述（可用測試斷言：mock monitoring 回 500，斷言畫面不含 `classStatus.empty` 文案）
- **SC-021**: 程式碼搜尋 `messages.record.saveFailed` MUST 出現於元件中而非僅定義處（dead string 清除驗證）
- **SC-022**: 學生端所有 `catch` 區塊 MUST NOT 僅含 `console.error` —— 每個 catch 都要有對應的使用者可見結果或明確註明為何不需要
- **SC-023**: 老師在懷疑某筆紀錄有問題時，能在任務細節頁 30 秒內查到「這筆被哪些座號、依什麼順序、在什麼時間處理過」（完整經手鏈，非僅最後一手）
- **SC-024**: 小老師遇到任務被老師刪除的情境時，能說出「老師把這個收起來了，要去問老師」而非嘗試重新掃碼（對應 vision「資料有生命週期」學習時機）
- **SC-025**: 任何 ACTIVE 且未封存的任務，不論是否指定小老師、是否設截止時間，MUST 至少受一條異常規則涵蓋 —— 涵蓋矩陣中不得存在空格
- **SC-026**: 學生因裝置離線而累積未上傳資料超過 24 小時的情境，老師 MUST 能從班級狀況 tab 察覺（透過任務停擺訊號），驗證心跳代理方案成立
- **SC-027**: 全班已登滿但未標記完成的任務 MUST NOT 產生停擺警示（假陽性驗證）
- **SC-028**: 成績類任務在登記未滿時被小老師標記完成前，學生端 MUST 曾顯示承諾確認提示（可測試：mock 登記 20/30 + 按完成 → 斷言提示出現、且未直接送出 `HELPER_COMPLETED`）
- **SC-029**: 登記已達班級人數時標記完成 MUST NOT 出現提示、繳交類任務標記完成 MUST NOT 出現此提示（「一律彈確認」反例與假陽性雙重驗證）
- **SC-030**: 任務被小老師標記完成但登記率 < 50% 時，老師 MUST 能從班級狀況 tab 察覺（規則三驗證）；登記率 ≥ 50% MUST NOT 觸發（閾值驗證）
- **SC-031**: 繳交類任務同樣受規則三涵蓋 —— `HELPER_COMPLETED` 且繳交率 < 50% MUST 判異常（繳交類納入驗證，確認與規則一、二的排除相反）

## Assumptions

- 門禁紀錄等級（不留前值）足以支撐老師的判斷需求。若實際使用中發現「查到人但不知道改了什麼」無法定案，需升級為保留前值或完整 audit log —— 此假設需在早期使用者回饋中驗證
- 「同一筆紀錄被多人連續覆蓋」在小學班級情境中屬低頻事件，因此只保留最後修改者、不保留完整變更鏈是可接受的取捨
- 學生看到「這一筆原本是 8 號登的」陳述句時，不會將其理解為指責 —— 沿用 003「視覺事實取代道德說教」已驗證的做法，但實際效果仍待觀察
- 老師會主動查閱任務細節頁（監視器的前提）。若實際上老師從不進入該頁，留痕機制的效力將大幅下降（vision 承諾裝置註腳已提出同樣警告），屆時需重新評估是否應升格為警示
- **任務停擺與裝置離線共用同一訊號是可接受的**（US6 核心假設）。老師收到「這個任務停擺了」時，不需要系統告知成因即可採取行動。若實際使用中老師反覆詢問「到底是誰的平板有問題」，則代理指標不足，需重新評估 Device entity
- 24 小時對「停擺」而言是恰當的閾值。改為滑動視窗後，觸發頻率會**高於**現行規則一（涵蓋範圍變大），實際噪音量需在早期使用中觀察；若過吵，優先調整閾值而非退回前置條件限制
- 17:00 為台灣國小放學時間的合理近似。老師若需要不同的截止時點，目前只能接受預設 —— 表單加入時間選擇屬後續 feature（對應 vision「給 KOL 老師彈性，給主流老師預設值」）
- 小老師看到「還有 N 個同學沒登記」會理解為提醒而非指責（沿用 003「視覺事實取代道德說教」），並據此判斷是真的完成還是漏登 —— 實際效果待觀察（US7）
- US7 的承諾核對只在承諾動作（標記完成）發生時介入，補的是「HELPER_COMPLETED 後異常規則停判」這一個空窗；它**不是**取代主動通知，老師仍需主動查閱任務細節頁才會看到最終完成度。真正讓老師「被通知後決策」仍待後續 feature 的通知通道（本 feature 明確排除）
- 50% 是規則三的合理起點，屬待觀察調整的參數（如同規則一的 24 小時）。若上線後過吵，優先調整閾值或改用班級基準法，而非移除規則三（US8 / FR-125）
- 老師收到規則三警示時，不需系統告知「是誤觸還是真的很多人沒交」即可行動 —— 沿用規則一「共用訊號、成因不影響行動」的假設（US8）
