## 第一部分：回饋資料能不能當研究資料？

### 誠實的答案：能，但要換一個框架

「收集了 bug 回報和意見回饋」本身是**資料集**，不是**研究**。差別只有一個：有沒有研究問題。

一份 bug 清單如果只被當成待辦事項，它是維護紀錄。但如果你問「**使用者對系統的理解，在哪些地方與設計者的意圖分歧？**」，同一批資料就變成研究資料。而這個問題在數位學習領域是真實存在的研究主題。

### 你應該用的框架：設計本位研究（Design-Based Research, DBR）

這是我看完你的 specs 之後最想跟你說的一件事。

**DBR 的核心是「在真實情境中反覆進行：設計 → 實施 → 分析 → 再設計」，並且它明確不要求大樣本。** 它的資料來源包含設計文件、設計決策的理由、實施過程的觀察、以及設計如何因為發現而修改。

你現在做的事，本質上**已經是** DBR 的一個完整循環，只是你沒有這樣稱呼它。這個框架對你有三個好處：

1. **它把「N 小」從缺點變成方法論特徵。** DBR 本來就是小樣本、深度、迭代的。你不需要為 N=8 道歉。
2. **它把你的 `specs/` 從開發文件變成研究資料。** 設計決策的軌跡在 DBR 裡是正式的資料類型，叫做 audit trail（稽核軌跡）。
3. **它把 bug 回報從維護紀錄變成假設檢驗。** 每一筆「使用者以為會 X，實際發生 Y」都是一次設計假設的檢驗。

> ⚠️ 我對 DBR 的描述是一般性的方法論理解。**寫進報告前請自己查一下中文文獻的標準定義與引用來源**（Design-Based Research Collective、Barab & Squire、以及台灣教育科技領域的中文回顧文章），確認你引用的定義和階段劃分符合該領域現行的說法。我不確定最新的文獻共識，這部分你要自己補。

#### 切入點二：`[B8]` vs `[B9]` 就是原則三的評估工具

**這一點你應該還沒想到，我覺得是這輪最有價值的發現。**

我在上一版的 bug 表單裡放了兩題：
- `[B8] 你以為會發生什麼`
- `[B9] 實際上發生了什麼`

> 「學生應該能夠說出『我在做什麼』，不只是『我在按什麼』。」

**每一筆 `[B8]` ≠ `[B9]` 的回報，就是一筆「心智模型與系統行為分歧」的記錄。** 這正是原則三要修的東西。你的 bug 表單意外地成了原則三的測量工具。

而且這批資料的性質很特別：它不是自評問卷（「你覺得系統好懂嗎」→ 社交性高分），而是**使用者在真實挫折情境下自發產生的心智模型陳述**。這種資料在可用性研究裡的價值很高，因為它沒有社交期許偏誤。

具體怎麼用：把所有 `[B8]` ≠ `[B9]` 的回報整理成分類表，看落差集中在哪些概念上（同步 / 權限 / 生命週期 / 資料格式）。這張表對應到 vision 那五個「為什麼時刻」，就能回答「哪些概念系統教得成功、哪些失敗」。

#### 切入點三：失敗與自我更正也是資料

你的 `推廣文案與使用須知.md` 第三節有兩段「更正我先前的說法」——原本判斷離線同步 bug 未修、換裝置找不回班級，查證後發現都不成立。

還有 `004/offline-sync-remediation.md` 的四個資料遺失缺陷（臉 A/B/C/D）：你先定了「系統必須保證技術正確性」的原則（原則四），然後發現自己的實作違反了它，然後修好。

**這條線比任何成效數字都能證明你在做有理念的設計。** 研究報告裡「我原本以為 X，證據顯示不是」的段落，是誠信的直接證明。審查委員讀論文最怕的就是「一路順風、什麼都成功」的敘事。

還有一個更精彩的案例：003 把「換座號」改成線上限定。理由是「syncQueue 去重鍵不含座號，離線換座號會讓前一座號未同步的登記被吃掉，破壞多人經手鏈」。

這是**技術限制迫使教育設計退讓**的具體個案 —— 你想給學生的彈性（隨時換座號），因為資料完整性的要求（原則四）而被收窄。這種張力在教育科技研究裡是很受歡迎的討論題材，因為它揭露了「理念」和「可實作性」之間的真實摩擦。

### 可以在回饋表單順便補的三題

1. **「你是怎麼知道這個系統的？」** → 對應 vision §4「兩種老師」，可分 KOL 型 vs 主流型
2. **「你目前用它取代了原本的什麼做法？」**（開放）→ 情境嵌入的資料，也是最好的採用動機證據
3. **「你有沒有調整過班上原本的小老師制度來配合這個系統？」** → 這一題測的是「工具反過來改變了組織實踐」，是 DBR 很在意的現象

## 第二部分：時間欄位的真相（讀之前必須知道）

**這一節是整份文件最重要的部分。如果搞錯，你所有的行為分析結論都是錯的。**

我把程式碼追過一遍，並在 `local.db` 上驗證。結論：

| 欄位 | 實際語意 | 來源 |
|---|---|---|
| `Record.createdAt` | **伺服器時間** | `schema.ts:15` 的 `$defaultFn(() => new Date())`，在 API route 執行 |
| `Record.updatedAt` | **伺服器時間** | `$onUpdateFn`；已實測確認 `onConflictDoUpdate` 時會更新（7 筆中 4 筆 `updatedAt != createdAt`） |
| `Record.syncedAt` | **伺服器時間** | `recordWrite.ts:115,119` 明寫 `new Date()` |
| **`RecordHandler.handledAt`** | **操作原始時間** | `api/sync/route.ts:92` 用 `op.timestamp`；`queue.ts:265` 送出 `op.createdAt`（**client 時鐘**） |

### 這代表什麼

**離線登記的 `Record.createdAt` 是「同步進來的時間」，不是「學生登記的時間」。**

假設一個學生在下課 10:15 離線登記，回家 20:30 連上 WiFi 才同步：
- `Record.createdAt` = 20:30 ← **錯誤的答案**
- `RecordHandler.handledAt` = 10:15 ← **正確的答案**

如果你用 `Record.createdAt` 畫「登記行為的時鐘分布圖」，你會得到一張「大家都在晚上登記」的圖，然後得出完全錯誤的結論。

### 所以：`RecordHandler` 是行為分析的主表，不是 `Record`

這一點在 `data-model.md` 裡沒有寫清楚（它只說 RecordHandler 是「誰依序動過這一格」的留痕機制，沒說它是唯一保有真實操作時間的表）。**建議在 `data-model.md` 補一段說明**，否則三個月後的你、或任何 AI agent，都會踩這個坑。

### 副產品：離線滯留時間可以推導

`Record.syncedAt`（伺服器收到）− 該格最後一手 `handledAt`（實際操作）= 離線滯留時間。

我在 `local.db` 上實測，確認可行：

```
記錄 10c455b3...  lag = 1,206,211 ms ≈ 20 分鐘   （離線後補同步）
記錄 d5193767...  lag = 0 ms                      （線上即時）
```

**但有兩個限制：**
1. `syncedAt` 每次 upsert 都被覆寫 → 只有「最後一次寫入」算得出滯留時間
2. `handledAt` 是 client 時鐘 → 平板時鐘偏差會污染結果，可能出現負值

這兩個限制都可以用一欄解決，見第四部分 P0-1 與 P0-3。

## 第三部分：現有資料就能做的分析（零程式碼修改）

### 圖一：登記行為的時鐘分布 ⭐ 核心圖

**證明的主張**：`vision.md` §6「解決的是時間控制權，不是總工作量」

**證明的主張**：`vision.md` §5「小老師在自己找得到的時間慢慢完成登記——下課、空堂、午休都可以」

## 第四部分：建議補上的欄位

排序標準：**「一欄換一張報告核心圖」的性價比**。我不建議你為了研究而大改 schema —— 3 個月時程下，每一個 migration 都是風險。

### P0：三個欄位，換到三張核心圖（強烈建議做）

#### P0-1. `RecordHandler.receivedAt`（伺服器時間）

**成本**：一欄 + `recordWrite.ts` 的 `appendHandlerIfNeeded` 多傳一個值

```typescript
// src/db/schema.ts，加在 recordHandler 的 handledAt 之後
receivedAt: integer('receivedAt', { mode: 'timestamp_ms' })
  .notNull()
  .$defaultFn(() => new Date()),
```

**換到什麼**：**每一次**寫入的離線滯留時間（不只最後一次）。目前靠 `Record.syncedAt` 推導只能算最後一次，因為 `syncedAt` 每次 upsert 都被覆寫。

有這一欄，圖四從「約略估計」升級為「精確測量」，而且每一手都有自己的滯留時間 → 可以畫「離線滯留時間的完整分布」。

#### P0-2. `RecordHandler.isOffline`（boolean）

**成本**：一欄；`api/sync/route.ts` 寫 `true`，`api/records/route.ts` 寫 `false`

```typescript
isOffline: integer('isOffline', { mode: 'boolean' }).notNull().default(false),
```

**換到什麼**：**不需要靠時鐘推導**就知道哪些登記是離線產生的。

**為什麼重要**：`handledAt` 是 client 時鐘。平板時鐘如果偏快 5 分鐘，推導出來的滯留時間會偏小甚至變負數。有這一欄，「離線比例」就是硬事實，不是推論。

這兩欄合起來，離線功能的成效分析從「可以推導但有雜訊」變成「乾淨可信」。而且這兩欄對產品本身也有用（老師端可以顯示「這筆是離線登記後同步的」）。

#### P0-3. `Task.helperCompletedAt` + `Task.reopenCount`

**成本**：兩欄 + `tasks/[roomId]/[taskId]/route.ts` 的 PATCH 加幾行

```typescript
helperCompletedAt: integer('helperCompletedAt', { mode: 'timestamp_ms' }),
reopenCount: integer('reopenCount').notNull().default(0),
```

PATCH 裡的邏輯（照著現有 `archivedAt` 的寫法就好）：

```typescript
if (status !== undefined) {
  // ...現有驗證...
  updateData.status = status;

  // 新增：標記完成的時刻（承諾裝置行為的時間點）
  if (status === TaskStatus.HELPER_COMPLETED) {
    updateData.helperCompletedAt = new Date();
  }
  // 新增：從完成/結案回到進行中 = 一次重新開放
  const wasLocked = existing.status === TaskStatus.HELPER_COMPLETED
                 || existing.status === TaskStatus.CLOSED;
  if (status === TaskStatus.ACTIVE && wasLocked) {
    updateData.reopenCount = existing.reopenCount + 1;
  }
}
```

> ⚠️ 注意：目前的 PATCH handler **沒有先讀取現值**（直接 `db.update(...).set(updateData)`）。要做 `reopenCount` 遞增就得先 `select` 一次舊的 status。這是一個實作上的小增量，記得加。

**換到什麼**：

1. **「小老師標記登記完畢」的時刻。** 目前這個狀態轉移**完全沒有時間戳** —— `status` 只有現值，`updatedAt` 會被任何欄位更新（改名字、改截止日）覆寫。而「標記完畢」是 vision §7 明確描述的**承諾裝置行為**：「標記完畢本身是一個承諾動作」。這個行為的時間點目前測不到。

2. **老師重新開放的頻率。** `vision.md` §7 自己寫：

   > 「待釐清：若小老師標記錯誤需要老師重新開放，這個情況發生的頻率是否會造成老師額外負擔？**建議在早期使用者回饋中觀察。**」

   **vision 自己點名要在早期觀察的東西，資料庫目前測不到。** 這是我認為最該補的一欄，因為它同時是產品問題（會不會造成老師負擔）和研究問題（承諾裝置的副作用）。

有了這兩欄，你可以畫一張「任務完整生命週期時間軸」：老師建立 → 小老師開始登記 → 標記完成 →（可能）老師重新開放 → 結案。這張圖就是 vision §5「我們做對了」場景的實證版本。

### P1：進場漏斗 —— 003 整個 feature 目前是零資料

#### P1-1. 新增 `JoinEvent` 表

**現況**：`/api/rooms/join/[code]` 是**純 GET 讀取，不寫任何東西**。選座號、自我聲明印章、換座號**全部在 client 的 localStorage**。

**後果**：003（小老師進場與身份體驗）整個 feature 的成效**完全沒有伺服器端資料**。你測不到：
- 有多少學生掃碼進來
- 選了座號之後有沒有真的開始登記（漏斗流失）
- 換座號的頻率（FR-074/075 那整套設計的使用率）
- 掃碼失敗 3 次升級為「去找老師」的觸發頻率（FR-065）

003 有 NFR-008（動畫 60fps）、SC-018 這些驗證條件，但**沒有任何「這個進場儀式有沒有達到效果」的行為指標**。

```typescript
export const joinEvent = sqliteTable(
  'JoinEvent',
  {
    id: text('id').primaryKey().$defaultFn(uuid),
    roomId: text('roomId').notNull().references(() => room.id, { onDelete: 'cascade' }),
    /** 'SCAN' 掃碼或輸入代碼成功 | 'SEAT_SELECTED' 選定座號 | 'SEAT_CHANGED' 換座號 */
    type: text('type').notNull(),
    /** SCAN 時為 null（還沒選座號） */
    seatNumber: integer('seatNumber'),
    deviceId: text('deviceId'),
    occurredAt: integer('occurredAt', { mode: 'timestamp_ms' })
      .notNull()
      .$defaultFn(() => new Date()),
  },
  (t) => [index('JoinEvent_roomId_occurredAt_idx').on(t.roomId, t.occurredAt)]
);
```

**換到什麼**：進場漏斗（掃碼 → 選座號 → 第一筆登記）的流失率。這是 003 唯一可能的成效指標。

**⚠️ 但這一項有兩個必須先處理的問題，我認為比技術實作更重要：**

**問題一：這是未成年人的行為資料。** 座號 + 班級代碼在 30 人的班級裡，對知道那個班的人來說**接近可識別**。你之前選擇「只收老師回饋」正是為了避開這個風險，而這張表會把未成年人的行為資料帶回來。

我的建議：
- 只存 `roomId` + `seatNumber`，**絕對不存姓名**
- 報告中只用彙整統計（「N 次掃碼中 M% 完成選座號」），**不呈現任何個別序列**
- 在使用須知明確揭露，並讓老師知道學生的操作會被記錄
- 如果你對這條線不確定，**寧可不做 P1-1**。圖一到圖八已經夠撐起一份報告了

**問題二：離線時寫不進去。** 學生離線進場，這個 POST 會失敗。要嘛接受資料有缺口（離線進場不計），要嘛塞進 syncQueue（複雜度上升）。**建議接受缺口並在報告中標註**，不要為了研究資料的完整性去動同步佇列 —— 那是 004 花了大力氣才穩定下來的東西，動它的風險遠大於收益。

#### P1-2. `deviceId` 真的實作（目前是死碼）

**現況**：我搜過整個 `src/`，`deviceId` 只出現在兩個地方：
- `src/types/index.ts:182` 宣告了 `deviceId?: string`
- `src/app/api/sync/route.ts:27` 在 destructure 裡宣告了

**client 從未產生它，也從未寫進資料庫。它是死碼。**

這正是 `anomaly-rules.md`「已知限制 → 無法指出是哪一台裝置」的成因。

**做法**：client 產生 uuid 存 localStorage（一台裝置一個，永不變），sync 時送出，寫進 `RecordHandler.deviceId`。

**換到什麼**：
- 一個班級用幾台裝置？（共用一台 vs 一人一機，這是「生生有平板」政策落地情況的實證）
- 同一台裝置有幾個座號用過？（共用裝置的實際樣貌）
- 哪一台裝置長時間未同步？（**這是產品功能，不只是研究需求** —— vision §2「圍欄的完整意思」明確說「當某台裝置長時間未同步時通知老師、讓老師能從該裝置觸發強制同步」，目前做不到就是因為沒有 deviceId）

**我認為這一項的優先序其實可以往上提到 P0**，因為它是 vision 明確要求的產品能力，研究價值只是附帶。

### P2：自我修正行為 —— 測「學生從錯誤中學習」

#### P2-1. 放寬經手鏈去重，改記 `revisionCount`

**這是我最喜歡的一個建議**，因為它同時服務產品（UI 完全不變）和研究（拿到關鍵指標）。

**現況**：`lib/recordHandlerRule.ts` 的 `shouldAppendHandler` —— 與名單最後一筆「座號或動作任一不同」才追加。所以**同一個人連續修改同一格，只留一筆**。

註解寫的理由是對的：「同一個人連續做同一件事（連續修正成績），只留一筆，避免灌爆名單」。這個 UX 判斷沒有問題。

**但問題在於**：`vision.md` §5「我們做對了」場景的核心句是：

> 「小老師發現有個同學的成績登錯了，他回想了一下操作步驟，**自己改掉了**。」

而 §2 原則三的整個立場是「讓學生自己判斷、自己排錯」。

**「學生自己發現錯誤並改正」是這個產品最想證明的學習行為，而它剛好被去重規則抹掉了。**

**做法**：規則判斷維持不變（不追加新列，UI 完全不受影響），但把最後一筆的 `revisionCount` +1。

```typescript
// schema.ts，加在 recordHandler
/** 這一手被同座號同動作連續重複的次數（0 = 只做過一次）。
 *  用於量測「自己發現錯誤並改正」的行為，不影響老師端顯示。 */
revisionCount: integer('revisionCount').notNull().default(0),
```

```typescript
// recordWrite.ts 的 appendHandlerIfNeeded
const last = await getLastHandler(taskId, studentId);
if (!shouldAppendHandler(last, { seatNumber, action })) {
  // 同座號 + 同動作連續 → 不追加新列（維持現有 UX），但記下他又改了一次
  await db.update(recordHandler)
    .set({ revisionCount: sql`${recordHandler.revisionCount} + 1`, handledAt })
    .where(/* 該格最後一筆的 id */);
  return;
}
```

> ⚠️ 實作細節：`getLastHandler` 目前只回 `{ seatNumber, action }`，要多回 `id` 才能 update。這是一個小改動。

**換到什麼**：
- 自我修正率（有 `revisionCount > 0` 的格子比例）
- 成績類 vs 繳交類的修正頻率差異
- 這是「學生在系統裡練習排錯」的**直接行為證據**，不是老師的觀察，也不是學生的自評

**這一項的研究價值我認為是所有建議裡最高的**，因為它測的是產品的核心教育主張，而且目前完全沒有替代的測量方式。

#### P2-2. `RecordHandler.prevValue`（存前值）

`data-model.md:224` 自己寫：「只留人、動作與順序，**不留前值**」，且升級為完整 audit log 已列在 `open-questions.md` 2026-07-20 待決。

**換到什麼**：修正幅度。60 → 85 vs 60 → 61 是不同性質的事（重新評分 vs 手滑改一位數）。

**但我建議放最後，甚至不做**，理由：
- 它是這批建議裡最重的（涉及成績資料的歷史留存）
- 它已經是 open-questions 的待決項，不該為了研究而搶先決定產品方向
- P2-1 的 `revisionCount` 已經能回答「有沒有自我修正」，`prevValue` 只是回答「修正幅度多大」，邊際價值不高

### P3：老師端行為 —— 建議先不做

`Room.lastViewedAt` 或一張 `TeacherActivity` 表，測「老師打開系統的頻率」。

對應 `vision.md` §6：「老師的角色應該是被通知後的決策者，而不是主動監控者」。
