## 零、先講策略：3 個月內你拿不到「成效」數字

這是設計題目之前必須先接受的事實，否則整份問卷會做白工。

推算一下時間軸：

| 時間 | 事件 |
|---|---|
| 8 月中～8 月底 | 暑假，國小老師不在班上。推廣文案可以準備，但沒有使用場景 |
| 9 月第 1–2 週 | 開學。老師忙開學事務，導入意願最低的時候 |
| 9 月中～10 月 | 真正的使用期。老師需要 **4–6 週**才累積得出「我對這系統的看法」 |
| 11 月中 | 你的 3 個月到期 |

也就是說，扣掉暑假與開學混亂期，**實際可用的觀察窗口大約 6–8 週**，樂觀估計能拿到 **5–15 份**有效的老師回饋。這個 N 撐不起「量化成效研究」。

### 所以策略要改成這樣

**不要押注在「量表數字好看」。** 碩班審查委員看到 N=8 的問卷、一份寫得極好的設計理據文件、加上 3 篇訪談逐字稿，評價會**高於** N=50 的自評滿意度問卷。因為前者顯示你會做研究，後者只顯示你會發問卷。

你手上真正的強項有三個，問卷只是第三個：

1. **`specs/vision.md` 本身就是罕見的素材。** 它有明確的教育理念立場（把管理權還給學生，而非賦能老師）、有理論引註（ZPD、commitment device）、有「刻意不做的事」的自我約束、有把設計原則拆成可驗證條目的紀律。這種文件在碩班備審資料裡非常少見。報告的骨幹應該是它，不是問卷。

2. **系統 log 是行為資料，證據等級高於問卷。** 你已經有每筆登記的時間戳與同步狀態了（FR-012）。「登記行為發生在一天中的哪些時段」可以**直接**證明你的核心主張——老師不再被綁在下課 10 分鐘。這是行為證據，不是自我報告。3 個月內完全做得到，而且不需要等 N 變大。

3. **問卷 + 訪談是佐證，不是主角。** 目標訂在「5–10 份問卷 + 3–5 場訪談」就夠了，而且問卷的最大功能其實是**幫你找到願意受訪的人**。

### 一句話

報告的敘事應該是：「我基於某個教育理念做了設計判斷 → 這些判斷體現在這些具體功能上 → 我用行為資料與初步回饋檢驗了它 → 這是我發現的落差與下一步」。這是研究者的樣子。「我做了一個 App 而且大家說讚」不是。

## 一、表單架構：兩份，但只公開一個入口

| | 表單 A：意見回饋 | 表單 B：老師使用經驗調查 |
|---|---|---|
| 目的 | Bug 回報 + 功能建議 | 研究佐證 |
| 對象 | 老師（含轉述學生遇到的問題） | 用過 ≥ 2 週的老師 |
| 何時填 | 隨時，遇到就填 | 你主動 email 邀請 |
| 入口 | Landing page + App 內「回報問題」按鈕 | 只透過 email 邀請 |
| 長度 | 分流後 8–12 題 | 30–35 題，約 8 分鐘 |
| Sheet | `feedback` | `study` |

**為什麼只公開一個入口？** 老師只會記住一個連結。推廣期同時給兩個，兩個都不會被填。表單 B 靠表單 A 收到的 email 來邀請——這也是表單 A 必須問 email 的原因。

**表單 A 用你原本的想法（單一連結、開頭分流）是對的。** 理由：Bug 和建議在老師心裡是同一件事（「我用了之後想說的話」），入口分開會讓人在「這算 bug 還是建議」上猶豫，而猶豫就是流失。Google 表單的區段分支（Section）完全支援這個做法。

代價是 Sheet 會變成一張很寬、半數欄位空白的表。這對 AI agent 其實**不構成問題**（空欄就是空欄，很好判斷是哪一類），對人眼才是問題。第四節會給對策。

## 二、表單 A：意見回饋

### 設計原則

1. **填答者是在「有點煩」的狀態下填的** → 必填題壓到最少（下面標 `*` 的才必填）
2. **不要問「請描述重現步驟」** → 老師不會寫步驟。改成拆解成四個小問題（B6–B9），每題只要一句話
3. **能用單選就不用開放題** → AI 好分類，老師好填
4. **選項用 `代碼｜中文`** → AI agent 能直接對應到程式碼路徑

### 表單開頭說明文字

> **小老師助手 — 意見回饋**
>
> 謝謝你願意花時間告訴我們。
>
> 這份表單可以用來回報問題，也可以提功能建議。**一次請只講一件事**，如果你有好幾件事，麻煩重複填幾次（這樣我們才好一件一件處理）。
>
> 填寫大約需要 3 分鐘。我們不會公開你的任何個人資訊。

## 三、表單 B：老師使用經驗調查（研究用）

**發送時機**：老師使用滿 2 週後，由你 email 主動邀請（名單來自表單 A 的 `[Z2]`）。
**預估作答時間**：8 分鐘。開頭要誠實寫出來，這會提高完成率。

### 開頭：知情同意（必須有）

> **關於這份問卷**
>
> 我是這個系統的開發者。這份問卷有兩個目的：一是了解系統實際用起來如何，作為後續改進的依據；二是**這些資料可能會以匿名、彙整後的形式，出現在我的學術報告或研究所申請資料中**。
>
> - 你的姓名、學校、班級都不會出現在任何報告裡
> - 開放題的內容如果被引用，會先移除所有可辨識的資訊
> - 你可以隨時不回答任何一題，也可以中途離開
> - 填答完成後如果反悔，寄信給我就可以要求刪除你的資料
>
> **`[C0] 我了解上述說明並同意`** `*` — 單選：`agree｜我同意` ／ `disagree｜我不同意（請直接關閉本頁）`

> ⚠️ **這段一定要寫。** 台灣的碩班申請專題報告一般不會要求 IRB 審查，但「有沒有知情同意」是審查委員判斷你懂不懂研究倫理的第一個訊號。這段話成本極低、加分很高。而且既然你已經決定只收老師（成人）的資料，倫理風險本來就低——把它做對是划算的。

### Part 0｜背景（用於分組與描述樣本）

- **`[D1] 任教年段`** — 單選：`low｜低年級` / `mid｜中年級` / `high｜高年級` / `mixed｜跨年段` / `other｜其他`
- **`[D2] 班級人數`** — 單選：`under-15｜15 人以下` / `16-25｜16–25 人` / `26-30｜26–30 人` / `over-30｜30 人以上`
- **`[D3] 擔任導師年資`** — 單選：`under-3｜3 年以下` / `3-10｜3–10 年` / `over-10｜10 年以上` / `not-homeroom｜我不是導師`
- **`[D4] 使用小老師助手多久`** — 單選：`under-2w｜2 週以內` / `2-4w｜2–4 週` / `1-2m｜1–2 個月` / `over-2m｜2 個月以上`
- **`[D5] 你用過哪些功能`** — 複選
  ```
  create-room｜建立班級
  import-excel｜Excel 批次匯入學生
  create-task｜建立登記任務
  grade-task｜成績類任務
  qrcode｜用 QRCode 讓小老師進班

  export｜匯出或複製報表
  anomaly｜看過系統的異常提醒
  restore｜用過還原連結換裝置
  ```
- **`[D6] 你班上的小老師是怎麼產生的`** — 單選
  ```
  assigned｜老師指定
  rotation｜輪流
  volunteer｜自願
  lottery｜抽籤
  mixed｜看情況不一定
  ```
  > 這是個有趣的**調節變項**。vision 第 4 節提到「被抽到的學生可能感到負擔」——如果資料顯示自願組的老師觀察到的學生投入度明顯較高，這是一個很好的討論點，也是你報告裡可以寫的「意料之外的發現」。

### Part 1｜工作的時間控制權

> **這一段測的是你的核心主張。** `vision.md` 第 6 節自己承認：「老師的負擔減輕的不是工作總量，而是工作的時間性」。
>
> ⚠️ **所以絕對不要問「這個系統幫你省了多少時間」。** 一來你自己說了總量沒減少，問了會得到難看的數字；二來這等於自打嘴巴，跟你的產品敘事矛盾。審查委員如果讀了你的 vision 又看到這題，會覺得你不了解自己的產品。
>
> **問時間性，不問時間量。** 這個一致性本身就是報告的亮點：「我的理論主張是 X，所以我設計了測量 X 的題目，而不是測量看起來比較漂亮的 Y」。

採**回溯式前後測**（retrospective pre-post）：在同一份問卷中同時問「使用前」與「使用後」。這在教育研究中是被接受的替代方案，避免要抓兩次資料。報告中要誠實標註這是回溯式設計，存在回憶偏誤。

**`[T1] 登記繳交或成績這類事 你通常在什麼時候處理`** — 複選 × 2（分「使用前」「使用後」兩題）
```
break-10｜下課 10 分鐘
lunch｜午休
free-period｜空堂
after-school｜放學後留在學校
at-home｜回家之後
during-class｜上課中順便處理
```

**以下用 1–6 同意度量表**（1 = 非常不同意，6 = 非常同意；**用偶數點，不給中間值**，避免大量填中間）
每題問兩次：`使用前` / `使用後`

| 代碼 | 題目 | 測什麼 |
|---|---|---|
| `[T2]` | 這些登記工作佔用了我原本可以備課或休息的時間 | 負擔感 |
| `[T3]` | 處理這些事情的時候 我常常被打斷 | 干擾程度 |
| `[T4]` | **我可以自己決定什麼時候處理這些事** | **時間控制權（核心）** |
| `[T5]` | 下課 10 分鐘對我來說是可以喘口氣的時間 | 恢復感 |

> `[T4]` 是整份問卷最重要的一題，因為它是產品主張的**直接測量**。報告裡要單獨拉出來討論。

### Part 2｜放手意願 × 掌控感

> **這是你的產品獨有的主張，也是最值得寫進報告的測量設計。**
>
> 推廣文案寫的是「管得少 管得住」；vision 說「『放手』和『失去掌控感』不是同一件事」。這句話聽起來很好，但要怎麼證明它成立？答案是：**同時測兩個構念，看它們能不能同時高**。
>
> - 只有「放手意願」高 → 老師是放生，不是放手
> - 只有「掌控感」高 → 老師還是自己在做
> - **兩個都高 → 你的主張成立**
>
> 這種「把設計主張拆成兩個彼此張力的構念再同時測量」的做法，本身就顯示你懂研究設計。這一段值得在報告裡用一整頁專門討論。

**放手意願**（1–6，× 使用前／後）
- `[E1]` 我願意把班級的登記工作交給學生做
- `[E2]` 我擔心交給學生做會出錯 *（反向題，計分時要反轉）*
- `[E3]` 交出去之後 我還是得自己再檢查一遍 *（反向題）*

**掌控感**（1–6，只問使用後）
- `[E4]` 即使我沒有全程盯著 我仍然知道班上的繳交狀況
- `[E5]` 如果學生登錯了 我有辦法發現
- `[E6]` 如果學生登錯了 我有辦法更正
- `[E7]` 我不需要每天打開系統 也不會漏掉重要的事

> `[E7]` 對應 vision 第 6 節那個尚未解決的問題：「老師的角色應該是被通知後的決策者，而不是主動監控者」。這題的分數如果偏低，就是你的通知機制（004）還沒做到位——這是很好的「已發現但尚未解決的問題」，寫進報告的限制與展望段落非常有說服力。

### Part 3｜科技接受

> 對齊 TAM（Technology Acceptance Model）的兩個核心構念。用既有理論框架的好處是報告可以引文獻，比自創題目強太多。你可以自己再去查 TAM 在台灣教育情境的中文化量表，會有更標準的題目措辭。

**知覺有用性**（1–6）
- `[U1]` 這個系統對我的班級管理有幫助
- `[U2]` 用了之後 我處理登記事務的方式變得比較好

**知覺易用性**（1–6）
- `[U3]` 我很快就學會怎麼用
- `[U4]` 第一次使用的時候 我不需要問別人就能完成建立班級
- `[U5]` **學生很快就學會怎麼用**
- `[U6]` 學生在操作上遇到困難時 大多能自己解決

> `[U5]`、`[U6]` 是這個產品特有的——一般 TAM 只測使用者本人的易用性，但你的產品有「老師採用、學生使用」的雙層結構。這個延伸本身就是報告可以討論的方法論貢獻。

**使用意願**
- `[U7]` 下學期我還會繼續使用（1–6）
- `[U8]` 你有多願意把這個系統推薦給同事？（0–10 線性量表，NPS）

### Part 4｜學生賦能（由老師觀察）

> **這是報告裡最漂亮的一段。** 下面五題直接對應 `vision.md` 第 2 節原則三那張表格裡的五個「為什麼時刻」。你可以在報告裡做一張對照表：
>
> | 設計意圖（vision 原文） | 對應功能（FR 編號） | 實際觀察（本問卷第 N 題） | 結果 |
>
> 這張表回答的是「設計意圖有沒有真的變成學習」，是整份研究最核心的問題。有這張表，你的報告就不是「我做了個 App」，而是「我提出了一組設計假設並檢驗它」。

**整體觀察**（1–6）
- `[P1]` 小老師在使用系統時 表現出責任感
- `[P2]` 小老師覺得擔任這個角色是有價值的事
- `[P3]` 學生會自己處理小問題 而不是馬上來找我
- `[P4]` 使用之後 學生對班級事務比以前更主動

**數位素養五時刻** — 每題用：`none｜完全沒觀察到` / `some｜有些學生` / `most｜大部分學生` / `na｜不適用`

| 代碼 | 題目 | 對應 vision 設計意圖 |
|---|---|---|
| `[P5]` | 學生知道成績欄只能填數字 會自己去切換輸入法 | 資料有格式和型別 |
| `[P6]` | 學生知道「還沒同步」代表資料還沒上傳 會去確認網路 | 系統有外部依賴 |
| `[P7]` | 學生知道權限是老師設定的 不是自己能改的 | 權限由體制決定 |
| `[P8]` | 學生知道同步之後 資料就是大家看得到的 | 資料同步後即共享 |
| `[P9]` | 學生知道截止之後不能改 要來找老師 | 資料有生命週期 |

> 注意這五題**問的是行為觀察，不是老師的猜測**（「學生會自己去切換輸入法」而不是「學生理解資料型別」）。老師觀察得到行為，觀察不到理解。這個措辭差異在研究方法上很重要，也是可以在報告裡說明的細節。

### Part 5｜開放題（3 個月內最有價值的資料）

> 樣本數小的時候，**質性資料的價值遠高於量化**。這五題是你的訪談素材庫，也是報告裡最能打動人的部分。

- `[Q1]` 請描述一次你印象最深刻的使用經驗（好的或不好的都可以）
- `[Q2]` 有沒有哪個時刻 讓你覺得學生從這個系統學到了什麼？請具體說說當時的情況
- `[Q3]` 有沒有哪個地方 讓你覺得「這個系統不懂老師在做什麼」？

## 四、Google Sheet 的欄位設計（給 AI agent 讀）

這一段是你補充的需求，也是最實務的部分。

### 4.1 核心原則：題目文字 = 欄位標題，且它一旦上線就不能改

**Google 表單的機制**：Sheet 的第一列標題就是題目全文。**你如果上線後修改題目文字，Google 會在 Sheet 新增一欄，舊資料留在舊欄**，兩欄並存。三次改動之後你的 Sheet 就毀了。

**對策**：
1. 題目文字用 `[代碼] 短標題` 的格式，例如 `[B1] 出問題的畫面`
2. 詳細說明全部放在題目下方的「說明」欄位（改說明**不會**動到 Sheet 欄位）
3. 上線前把所有題目文字定稿，上線後只改說明

這一招的額外好處：你在 GitHub issue、報告、跟 AI agent 對話時，都可以直接說「B7 那欄」，不用複述整句題目。

### 4.2 選項用 `key｜中文` 格式

```
helper-record｜小老師登記畫面
```

- `key` 部分穩定、英文、可直接對應到程式碼路徑或 spec 編號
- `｜` 用**全形直線**，不要用半形 `|`，也不要用逗號或斜線（避免跟 CSV 分隔符、複選題串接衝突）
- 中文部分給人看，隨時可以微調中文而不影響 key 的辨識（雖然改了還是會動到欄位值，所以最好也別改）

AI agent 拿到 `helper-record｜小老師登記畫面` 時，用 `｜` 一切就得到機器可讀的 key，不用做語意猜測。

### 4.3 複選題的雷

Google 表單把複選答案用**半形逗號 + 空格**串在同一格：
```
self-report｜學生自己標記..., public-board｜班級公開看板..., teacher-push｜有異常才推播...
```

所以：**選項文字裡絕對不能出現半形逗號**。本提案的所有複選選項都已用空格取代逗號。這條規則一旦破掉，後續解析會靜默出錯（不會報錯，只會分錯），很難發現。

### 4.4 一列 = 一個事件

表單開頭要明講「一次只講一件事」。如果老師在一份回應裡塞三個 bug，你的統計、分類、優先序全部會亂掉，AI agent 也沒辦法把它拆開歸類。

### 4.5 不要動「表單回應」分頁，另開衍生分頁

Google 會覆寫「表單回應 1」分頁，你在上面加的欄位可能被推移或清掉。

**做法**：另開一個分頁 `triage`，第一列用公式從原始分頁拉資料：

```
=QUERY('表單回應 1'!A:Z, "SELECT A, B, C, D, ... WHERE A IS NOT NULL", 1)
```

然後在 `triage` 分頁**手動**加這幾欄（這些是 AI agent 最需要、但表單收不到的資訊）：

| 欄位 | 內容 | 用途 |
|---|---|---|
| `狀態` | `new` / `investigating` / `fixed` / `wontfix` / `duplicate` | 追蹤 |
| `分類` | `sync` / `ui` / `data-loss` / `misunderstanding` / `perf` | 你的判斷 |
| `對應 spec` | 例如 `004 FR-081` / `003 FR-075` | **讓 AI agent 直接跳到正確的 spec** |
| `對應檔案` | 例如 `src/components/RecordForm.tsx` | 讓 AI agent 直接定位程式碼 |
| `GitHub issue` | `#12` | 串起來 |
| `優先序` | `P0` / `P1` / `P2` | 排程 |
| `備註` | 你的判斷過程 | 你三週後會忘記，AI agent 也需要 |

> **`分類` 裡的 `misunderstanding` 這一項很重要。** 依 vision 原則三，如果老師或學生「以為系統壞了但其實是誤解」，那不是 bug，是**介面沒把概念講清楚**——而這正好是 vision 說要修的東西（提示要指向概念，不只是行動）。把這類回報單獨標記出來，你會得到一份「哪些地方的心智模型沒對上」的清單，這對產品和報告都很有價值。

### 4.6 給 AI agent 的時候，附一份欄位字典（codebook）

這是差別最大的一招。你把 Sheet 匯出成 CSV 丟給 AI agent 時，同時給它一份 `codebook.md`：

```markdown
# feedback 表單欄位字典

## 資料範圍
每一列 = 一筆使用者回饋。B 開頭欄位僅在 A2=bug 或 both 時有值，
S 開頭欄位僅在 A2=idea 或 both 時有值。空白欄位代表不適用，不是遺漏。

## 欄位

| 欄位 | 型別 | 選項 | 對應 spec |
|---|---|---|---|
| 時間戳記 | datetime | Google 自動 | — |
| [A1] 你的身分 | 單選 | teacher / helper / other | vision §2 原則二 |
| [B1] 出問題的畫面 | 單選 | helper-record → src/components/RecordForm.tsx, 004 spec<br>teacher-restore → src/app/teacher/page.tsx, 005 spec<br>... | 各 feature |
| [B5] 畫面上當時的同步狀態 | 單選 | synced / pending / syncing / failed / not-noticed / none | 004 FR-081 SyncIndicator |
| [B11] 嚴重程度 | 單選 | blocked / workaround / cosmetic / **data-loss** | data-loss 屬 vision 原則四「系統必須保證不發生」，一律 P0 |
| [S5] ... | 複選 | 半形逗號分隔；選項對應 vision §7 待用靈感 | vision §7 |

## 分析時的注意事項
- [B3]=student-told 的回報，B6–B9 的描述經過老師轉述，可信度較低，
  追查前建議先確認
- [B11]=data-loss 的回報一律優先處理，不論頻率
- [S3] 有具體答案的建議 = 真實痛點（已有 workaround）；
  [S3] 空白或「沒想過」的 = 想像需求，優先序降低
```

有這份 codebook，AI agent 讀 Sheet 的正確率會差非常多——它不用從中文題目猜語意，直接照字典查。

### 4.7 最大的槓桿：App 內用「預填連結」自動帶入情境

> **這一節是整份提案裡投入產出比最高的一項。** 它解決的不是「表單好不好填」，而是
> **「老師記不清楚」這個根本問題** —— 而且實作成本極低（本質上就是組一個 URL）。

#### 核心想法

在 App 裡加一個「回報問題」按鈕，點下去時**用程式組出一個已經預填好的表單網址**，自動帶入：

| 帶入什麼 | 從哪裡拿 | 為什麼比老師自己填準 |
|---|---|---|
| 目前路由 → `[B1]` 畫面 | `usePathname()` 對照路由表 | 老師常說不出「我在哪個畫面」，而路由是精確的 |
| 角色 + UA → `[B2]` 裝置 | localStorage 有無 `teacherId` + UA | 老師可能忘記是自己的電腦還是學生的平板 |
| 連線狀態 → `[B4]` 網路 | `isServerReachable()` | **老師的印象最不可靠的一項**（lie-fi 時他以為有網路） |
| 同步狀態 → `[B5]` | `SyncIndicator` 當下的狀態 | 老師大多「沒注意看」，但這是最關鍵的分流資訊 |
| 現在時間 → `[B12]` | `new Date()` | 老師事後回想常差好幾小時，對不到 server log |
| 班級代碼 → `[B13]` | 目前 room | 要老師去翻代碼就會放棄 |
| 部署版本 → `[X1]` | build 時注入的常數 | 老師根本不知道有這個東西 |

**結果：老師只要寫 `[B6]`–`[B9]` 那四句話（本來想做什麼 / 按了哪些地方 / 以為會發生什麼 /
實際發生什麼），其餘七欄都是機器測到的事實，不是他的回憶。**

這一招同時讓 `[B4]`+`[B5]` 這組「判斷是不是同步問題」的關鍵資訊從「大概八成的人會選『不確定』」
變成「100% 準確」—— 對 004 範疇的 bug 調查來說，差別非常大。

#### 實作

Google 表單的預填連結格式是 `?usp=pp_url&entry.<id>=<值>`。`entry` id 有兩種取得方式：
表單編輯畫面選「取得預先填入的連結」手動抄，或用 `google-form-builder.gs` 的
`logEntryIds()` 一次全部印出來（推薦，不會抄錯）。

```typescript
// src/lib/feedback.ts

// ⚠️ 這些字串必須與表單選項**一字不差**（含全形｜與中文），否則該欄預填會靜默失效。
//    建議與建表腳本的 OPT 常數共用同一份來源。
export const FEEDBACK_OPTIONS = {
  screen: {
    teacherDashboard:   'teacher-dashboard｜老師首頁（儀表板）',
    teacherRoomStudents:'teacher-room-students｜班級－學生名單',
    teacherRoomTasks:   'teacher-room-tasks｜班級－任務清單',
    teacherRoomStatus:  'teacher-room-status｜班級－班級狀況',
    teacherTaskDetail:  'teacher-task-detail｜任務細節／結果頁',
    teacherQrcode:      'teacher-qrcode｜QRCode 分享視窗',
    teacherImport:      'teacher-import｜Excel 匯入學生',
    teacherRestore:     'teacher-restore｜還原連結／換裝置',
    joinScan:           'join-scan｜小老師掃碼進班',
    joinSeat:           'join-seat｜選座號／自我聲明',
    helperTaskList:     'helper-task-list｜小老師任務清單',
    helperRecord:       'helper-record｜小老師登記畫面',
    unknown:            'unknown｜不確定／想不起來',
  },
  network: {
    online:   'online｜正常',
    unstable: 'unstable｜不太穩',
    offline:  'offline｜完全沒網路',
    unknown:  'unknown｜不確定',
  },
  // device / syncState 同理
} as const;

// 由 logEntryIds() 產生
const FORM_BASE = 'https://docs.google.com/forms/d/e/<FORM_ID>/viewform?usp=pp_url';
const ENTRY = {
  B1:  'entry.111111',   // 出問題的畫面
  B2:  'entry.222222',   // 出問題的裝置
  B4:  'entry.333333',   // 當時的網路狀況
  B5:  'entry.444444',   // 畫面上當時的同步狀態
  B12: 'entry.555555',   // 大約發生時間
  B13: 'entry.666666',   // 班級代碼
  X1:  'entry.777777',   // 系統版本
} as const;

export interface FeedbackContext {
  screen: string;      // FEEDBACK_OPTIONS.screen 的某個值
  device: string;
  network: string;
  syncState: string;
  occurredAt: Date;
  roomCode?: string;
}

export function buildFeedbackUrl(ctx: FeedbackContext): string {
  const p = new URLSearchParams();
  p.set(ENTRY.B1, ctx.screen);
  p.set(ENTRY.B2, ctx.device);
  p.set(ENTRY.B4, ctx.network);
  p.set(ENTRY.B5, ctx.syncState);
  // ⚠️ 日期時間題的預填格式見下方「已知地雷」
  p.set(ENTRY.B12, formatDateTimeForForm(ctx.occurredAt));
  if (ctx.roomCode) p.set(ENTRY.B13, ctx.roomCode);
  p.set(ENTRY.X1, APP_VERSION);
  return `${FORM_BASE}&${p.toString()}`;
}
```

#### 離線時的處理（必須做，否則這個按鈕在最需要的時候壞掉）

**Google 表單是外部網站，離線時開不了。** 而且諷刺的是，**最需要回報的問題往往就發生在離線的時候** ——
如果離線時按「回報問題」只跳出一個打不開的頁面，這個功能等於在關鍵情境下失效。

處理方式（三段，依可用性遞減）：

```typescript
// src/lib/feedback.ts

const PENDING_KEY = 'little-helper-pending-feedback';

export async function openFeedback(ctx: FeedbackContext): Promise<FeedbackOutcome> {
  const url = buildFeedbackUrl(ctx);

  // 依 003 FR-075 的教訓：用實際探測，不用 navigator.onLine
  // （後者在 DevTools 離線模擬與 lie-fi 都仍回報 true）
  const reachable = await isServerReachable();

  if (reachable) {
    window.open(url, '_blank', 'noopener');
    return { kind: 'opened' };
  }

  // 離線：把整包情境存起來，等連線後再提示
  const pending = { ...ctx, occurredAt: ctx.occurredAt.toISOString(), url };
  localStorage.setItem(PENDING_KEY, JSON.stringify(pending));

  // 同時嘗試複製到剪貼簿，讓老師可以立刻貼到記事本或 LINE 給自己
  try {
    await navigator.clipboard.writeText(buildPlainTextSummary(ctx));
    return { kind: 'savedAndCopied' };
  } catch {
    // 剪貼簿在非安全context或未授權時會失敗 → 退回只存起來
    return { kind: 'savedOnly' };
  }
}
```

三種結果對應三種提示文字（都要進 `messages/zh-TW.ts`，NFR-001）：

| 結果 | 提示文字 |
|---|---|
| `opened` | （不用提示，表單已開） |
| `savedAndCopied` | 「現在沒有網路，沒辦法送出回報。**問題的狀況已經幫你記下來也複製起來了**，等有網路的時候畫面上會提醒你。」 |
| `savedOnly` | 「現在沒有網路，沒辦法送出回報。**問題的狀況已經幫你記下來了**，等有網路的時候畫面上會提醒你。」 |

然後在連線恢復時（沿用既有的 online 偵測），若 `PENDING_KEY` 有值就顯示一個不擋操作的提示條：
「你之前有一個問題還沒回報，要現在填嗎？」→ 點了就開存下來的 `url`，送出後清掉 key。

**設計上的注意**：這個提示條要能被關掉，而且關掉就清掉 key。否則老師會被一個永遠關不掉的
提示條煩到 —— 那違反 vision 原則一「不要過度確認」。

#### 已知地雷

1. **選項字串必須一字不差。** 單選/下拉的預填值若與選項文字不完全相同（差一個全形空格也算），
   該欄會**靜默留空**，不會報錯。所以選項常數要有單一來源，不要在 App 和表單各寫一份。
   建表腳本 `google-form-builder.gs` 的 `OPT` 常數就是那份來源。

2. **日期時間題的預填格式要實測。** `[B12]` 是 DateTime 題，Google 對日期時間的預填參數格式
   不一定是單一 `entry.N=`（可能拆成 `entry.N_year` / `_month` / `_day` / `_hour` / `_minute`）。
   **做法：先在表單 UI 用「取得預先填入的連結」填一個日期時間，看它產生什麼參數，再照著組。**
   我沒有實測過這一項，不要照抄我上面的 `formatDateTimeForForm`，先去看一眼實際格式。
   如果格式太麻煩，退路是把 `[B12]` 改成簡答題、由 App 填入 ISO 字串。

3. **預填值老師仍可修改。** 這是好事（他能更正機器猜錯的），不用鎖。

4. **不要把 email 或還原連結放進預填。** 還原連結是永久不可撤銷的 bearer token（005 NFR-017），
   絕對不能出現在任何外送的 URL 裡 —— 那會把它送進 Google 的伺服器日誌與瀏覽器歷史。
   班級代碼可以（它本來就是給學生看的），`teacherId` 不行。

5. **「回報問題」按鈕放哪裡。** 建議：老師端放進 `SettingsMenu`（沿用 005 的既有入口）；
   小老師端**不要放** —— 依 vision §4，小老師遇到問題該做的事是「去找老師」，
   而不是自己填一份英文夾中文的表單。真要放，就放一個「告訴老師」按鈕，把當下狀態存進
   localStorage 讓老師端看得到，不要導向 Google 表單。

#### 額外要在表單裡加的一題

- **`[X1] 系統版本`** — 簡答（選填），說明寫「這一欄會自動填入，請不要修改」。
  用來對應 git commit 或部署版本，判斷「這個 bug 是哪一版的」。
  手動填表的人留空即可，不影響。

### 可以直接產出的三張圖

**圖一：登記行為的時間分布（一天 24 小時的直方圖）**

多少筆登記是在離線狀態下產生的？從登記到同步隔了多久？這驗證的是「離線可用」這個賣點到底有沒有被真的用到。如果離線比例很低，那你在離線同步上投入的大量工程（004 的整個 remediation）就要重新評估價值——這種「發現自己的假設錯了」的段落，寫進報告比一路順風更有說服力。
